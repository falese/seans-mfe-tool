seans-mfe-tool · how it works

Breaking up a big app

Many products start as one big web app that one team built. Over time, many teams need to change it, and they get in each other's way. This toolchain splits that app into smaller pieces, so each team can own, change and release its own piece. The product still looks and works the same to the people who use it.

This page explains how each step works and what it must do. Read it as a requirements prototype: some steps are built, some are next, and each one says which.

Before you start

Words we use

The big app
The existing app we are splitting up. Engineers call it a monolith.
A piece
One part of the product that one team owns, such as "orders" or "profile". Engineers call it a micro-frontend, or MFE.
Shell
The frame around the pieces: the header, the menu, and the space where each piece appears.
Screen area
One visible part of a screen, such as a table, a panel or a card.
Backend
The service a screen gets its data from.
Data helper
A small service for one piece. It fetches that piece's data from the backends. Engineers call it a BFF.
API description
A document that lists what a backend can be asked and what it answers. Engineers call it an OpenAPI spec.
The plan
One file listing the proposed pieces and why. Everything else is built from it.
The workspace
The review screen for product owners. It shows the plan on the real screens and changes it only through the same named actions. Approving there records exactly which version of the plan was approved.
Figure 1 — the steps

Eight steps, and two decisions only people make

The order is the one a careful team would follow by hand. First, find out what the app does. Then decide where to cut it, and agree that. Then move one piece at a time, checking after each move that nothing changed. The tools do the finding, suggesting and checking. People decide where to cut, and when the work is finished.

Step 1 — watch the app built

Use the app like a person would, and record everything

A browser opens the big app and follows a set of short scripts called journeys, such as "open the home page, click Docking, open a berth". It also explores the app by itself, following every link it can find. At each step it notes what is on the screen, which piece of code drew each part, what data the screen asked for, and any errors. It saves a screenshot too.

Goes inThe running big app, and a few journeys (optional)
What happensA browser clicks through it, with the clock frozen so dates never change between runs
Comes outA recording: screens, screen areas, data requests and answers, errors, screenshots
It must
  • Name the piece of code behind each screen area, by reading the labels React adds while an app is in development.
  • Link each data request to the screen area that shows its answer.
  • Keep every answer, so the same journeys can be replayed later with exactly the same data and no live backend.
  • Never press buttons or submit forms while exploring, so it cannot change the app's data.
  • Handle older and newer apps alike: different React versions, and both kinds of web address (/page and /#/page).
Step 2 — read the code built

Find out what reaches what

The recording shows what happened. The code shows everything that could happen, including screens nobody visited. This step reads the code and builds a map: which address shows which screen, which files each screen uses, and which data each screen asks for. It follows the request all the way to the backend address. It also finds data a screen uses without showing it, which is a hidden link between areas that screenshots can't reveal.

Goes inThe app's source code, and the recording from step 1
What happensThe code is read, not run; then the map is matched against the recording
Comes outA map: screens, files, data requests, hidden links, the old tests sorted, and who changes what
It must
  • Explain every data request the recording saw by pointing at the code that makes it.
  • Sort the app's existing tests into keep, rewrite or throw away, with a reason for each.
  • Mark a file used by several screens as shared, not hand it to one of them.
  • Read the common ways apps are written: plain JavaScript or TypeScript, older and newer routing, and the usual ways of storing and fetching data.
Step 3 — suggest the pieces built

Group the files into pieces, and show the reasons

The strongest clue is data. Screens that show the same data usually belong together. The tools start from the app's screens, give each file to the screen that uses it, and pull in the files that share a screen's data. Every suggested piece gets a score for each clue, so a reviewer can see why the line is where it is. The same rules always give the same answer, so the result can be checked and repeated.

It must
  • Give every piece the reasons behind it, not just a name.
  • Flag every hidden link, where one piece reads another piece's data, as a risk to fix.
  • Tell apart an app with one backend from one whose requests go to several backends.
  • Check that the plan can really be built: every piece must pass the same checks a hand-made one does.
Step 3, continued — data built

Give each piece a description of the data it needs

Each new piece gets its own data helper, and a data helper needs an API description of every backend it talks to. Old apps rarely have one. So the tools write one from the recording: every question the app asked and every answer it got. They then compare it with the code, so questions the recording missed still appear. Each piece's data helper gets only the questions that piece asks, plus the recorded answers as sample data for demos.

It must
  • Describe only what the app was seen or written to ask. Never guess at more.
  • Mark the description as written by the tools, and record which recorded request each part came from.
  • Prefer the backend's own description when it has one, and report where the two disagree.
Step 4 — people agree decision

Review the plan on the real screens

A plan written as a list is hard to judge. So the tools turn it into a review package: a written summary, and every screen of the app with a coloured box around each suggested piece. That is produced both as a web page and as a Figma page. The reviewer can then approve the plan, or rename, merge or split pieces, or move a file. Each change is a named action, so everything connected to it moves too, and the plan is checked again straight away.

It must
  • Show every suggested piece on at least one real screen, and warn about any piece no screen shows.
  • Keep the plan valid after every change; an invalid change is refused with a reason.
  • Work without the internet: the Figma page carries its own screenshots.
  • Treat approving the plan as the decision. Nothing is built before it.

The workspace: the same review, for product owners

A product owner should not have to read a plan file or open a terminal. The workspace is a screen where they see the plan drawn over the real app, as below, and shape it: merge or split pieces, rename them, move a file, leave comments, and approve. It keeps nothing of its own. Every click is one of the same named actions, so it is checked the same way, and the plan file stays the only record. The AI agent works there too. It answers a question such as "split hazards out of cargo" with suggested changes. Each suggestion is tried on a copy of the plan first, and nothing changes until a person accepts it.

An engineer opens it with one command, decompose:workspace, and it runs on that person's own machine. It is itself one of the pieces the platform builds: a generated MFE with four screen areas (the map, shaping, the agent, approval) and its own data helper.

The workspace must
  • Keep nothing of its own: a reload, a second tab or a restart shows the same plan.
  • Change the plan only through the named actions, so an invalid change is refused with a reason.
  • Hold every agent suggestion until a person accepts or rejects it, and show whether it would still work.
  • Record who approved, when, and exactly which version of the plan. Any later change to the pieces makes the approval out of date. A comment does not.
  • Run on the person's own machine first, and be built so the same screen can later be hosted.
Figure 4 — Figma

Turn any running screen into an editable Figma design

Separately from the review boxes, the tools can turn any screen of a running app into a real, editable Figma design. It is made of frames, text and shapes, not a flat picture. Designers start from what is actually live, not from an old mock-up. It works on any web app, split up or not.

It must
  • Include only what you can see on the screen, including content inside reusable web components.
  • Use Figma auto-layout only where it matches the page exactly; elsewhere keep exact positions.
  • Say what it could not copy. Gradients become a plain colour, only the first shadow is kept, and video, canvas and embedded frames become labelled placeholders.
  • Be checked in the Figma desktop app before anyone relies on it. So far it has only run against a stand-in for Figma (issue #434).
Steps 5 to 7 — build, move, switch over next

Move one piece at a time, with the old app still running

The pieces are not swapped in all at once. First, the whole old app is wrapped up as one piece of its own, so the new shell can show it unchanged. Then, one screen area at a time, that area is pointed at its new piece instead of the old app. After every switch, step 8 checks that nothing changed. If something did, that one switch is undone.

Step 5 · buildAn empty piece and data helper for each area in the plan, plus the old app wrapped as one piece. At first every screen still shows the old app.
Step 6 · moveEach screen's code, and the tests marked keep, move into its piece. Tests marked rewrite are replaced with ones that check behaviour.
Step 7 · switch overOne screen area at a time moves from the old app to its new piece. Each switch is its own small, reviewable change.
It must
  • Keep the product working at every point: users see no difference while the work goes on.
  • Never switch more than one screen area without passing the check in step 8.
  • Only write into the parts of each piece that developers own, never over files the platform generates.
Figure 5 — step 8, check nothing changed built

Replay the same journeys and compare

The check takes the recording from step 1 and replays its journeys against the new version. It uses the same frozen clock and the same recorded answers, so the data cannot differ. It then compares the two runs screen by screen. Run first against the old app itself, it proves the journeys give the same result every time. After that, any difference means the app changed.

It must
  • Pass against the old app itself before it is trusted to judge a new version.
  • Report a change once, in the screen area that caused it, not in every area around it.
  • Allow no visual difference unless a person sets an allowance on purpose.
  • Name what the journeys never visited, so nobody mistakes "not checked" for "unchanged".
Does it work?

Tested on our own app, and on two that nobody here wrote

The short answer On our reference app, built to be split, it found the seven planned pieces. On two unrelated public versions of the same blogging product, written by different people with different tools, it found the same eight pieces in both. It also explained every data request in both, and both passed the step 8 check against themselves. The outside apps also exposed sixteen gaps the reference app never could; all are fixed.

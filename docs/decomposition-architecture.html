seans-mfe-tool · how it works

Decomposing a monolith

Many products start as a monolith, which is one codebase that a single team builds. As more teams change it, they block one another. These tools split the monolith into pieces, so that each team owns, changes and releases its own piece and users see the same product.

This page explains each step, who does the work in it, and the rules that the step must follow. It ends with the evidence that the tools meet those rules.

Before you start

Terms

Monolith
The existing application that you decompose, which is one codebase that ships as one unit.
Piece
A bounded part of the product that one team owns, changes and releases on its own, for example orders or profile. It ships as one micro-frontend (MFE), and the plan and the workspace call it a domain.
Shell
The host application that composes the pieces. It provides the header, the navigation and the space where each piece renders.
Screen area
A rendered part of a screen, for example a table, a panel or a card, which the capture records as a region.
Backend
A service that supplies data to the screens.
Data helper
A small service for one piece, also called a backend for frontend (BFF). It gets the data of that piece from the backends and returns it in one consistent shape.
API description
A machine-readable list of what a backend accepts and returns, in OpenAPI format.
Tools
Code that follows fixed rules, so that the same input always gives the same output. No model runs inside the tools.
Agent
An AI assistant that makes judgment calls, for example a name or a split. It works through the same commands that a person uses, or as the hosted model in the workspace. The tools check each result.
The plan
One file, decomposition.yaml, that lists the proposed pieces with the evidence for each. The tools derive everything else from it.
Bundle
The folder of data that steps 1 to 3 produce: the recording, the map of the code, the plan and the screens. Apps and tools read it.
Publish
To send the plan and its evidence to the workspace.
The workspace
The tool where people review, discuss, shape and approve the plan, either on the machine of the engineer or as a hosted service. It shows the plan on the real screens, changes the plan only through named actions, and records the exact version that a person approves.
Figure 1 — the steps

The eight steps and the two approvals by people

A careful team follows this order by hand. It first finds out what the app does, then decides where to cut it and agrees on the cuts. After that it moves one piece at a time and checks after each move that nothing changed. The tools find, suggest and check, and people approve both the cuts and the finished work.

Who does the work

Which steps use tools, an agent and people

Each step has up to three kinds of worker. Tools do the work that must give the same result every time. An agent helps where the work needs judgment, such as a name or a split, and people make the decisions. The tools check each result of the agent before it counts.

Steps 1 and 2 need no agent, and step 3 gives the same draft with or without one. The agent is optional in steps 1 to 4, and it does real work only in steps 5 and 6.

Because tools do most of the work, most results are repeatable and can be tested. The agent never acts alone: the tools check what it proposes, and people approve what is built. The one place where an agent changes real code is step 6, and the check in step 8 protects it. That check covers only the behavior that the journeys use, and its report lists the routes that no journey visits.

The rules that keep the agent safe
  • An agent never writes the files that the platform generates. It writes only the files that developers own.
  • The tools try each change of the agent on a copy of the plan. They drop a change that breaks the plan and show the reason.
  • Nothing is built before a person approves the plan.
  • Each switch in step 7 passes the step 8 check and has its own pull request.
  • The key for the hosted model comes from the environment only, and a person can switch the agent off.
Step 1 — watch the app

Watch the app and record what it does

A browser opens the monolith and follows short scripts that are called journeys, for example: open the home page, click Docking, open a berth. It also explores the app alone by following each link that it finds. At each step it records what is on the screen and which code drew each part. It also records which data the screen asked for and any errors, and it saves a screenshot.

ToolsDrive the app in a browser and record it, so that the same journeys always give the same recording.
AgentCan write journeys from the route table and the forms, but this is optional.
PeopleGive the address of the app, and write journeys if you want to.
How it works
  1. Someone starts the monolith in development mode and gives its address to the tools.
  2. The tools open the app in a browser like a user, run each journey, and then follow links on their own.
  3. After each step, the tools write down what the screen shows and which code drew each area.
  4. They also write down each question that the screen sent to a backend, together with the answer.
  5. They freeze the clock and keep the answers, so that a later run can replay the same session.

Example. On the reference app, the capture finds that the docking board and the traffic log both ask the harbormaster backend for docking data.

An example journeys file

A person can give this file to step 1. Each journey starts in a fresh browser. Each line is one action. A selector can be any Playwright selector. The file is examples/meridian-monolith/journeys.yaml.

journeys:
  - name: station-overview
    steps:
      - goto: /
      - wait: 300
      - click: "a[href$='docking']"
      - click: "a[href$='life-support']"
  - name: cargo-and-crew
    steps:
      - goto: /cargo
      - wait: 300
      - click: "a[href$='crew']"
      - click: "a[href$='concourse']"

The command that uses the file is seans-mfe-tool decompose:capture http://localhost:5090 --journeys journeys.yaml. The other actions are fill and press. Without a file, the tools only explore links.

Goes inThe running monolith, and optional journeys
Comes outA recording: screens, screen areas, data requests and answers, errors and screenshots
It must
  • Name the code behind each screen area. Read the labels that React adds in development mode.
  • Link each data request to the screen area that shows the answer.
  • Keep each answer, so that the same journeys can run again with the same data and no live backend.
  • Never press buttons or send forms during exploration, so that the data of the app does not change.
  • Work with old and new apps: support different React versions and both kinds of web address (/page and /#/page).
Step 2 — read the code

Read the code and connect it to the recording

The recording shows what happened, and the code shows everything that can happen, including screens that nobody visited. This step reads the code and makes a map. The map shows which address shows which screen, which files each screen uses, and which data each screen asks for. The map also shows data that a screen uses without showing it, which is a hidden link between areas that a screenshot cannot reveal.

ToolsRead the source code with a parser and do not run the app, so that the same code always gives the same map.
PeopleNothing to do in this step.
How it works
  1. The tools read each source file and the way that files import each other.
  2. They find the routes and decide which screen each file belongs to. A file that several screens use is marked as shared.
  3. They find each backend call in the code, also when a helper function hides it, and match it to the calls in the recording.
  4. They read the tests and mark each one keep, rewrite or throw away, with a reason.

Example. The hazard summary shows no docking data on screen, but the code reads that data to filter. The recording cannot see this, so the map shows it as a hidden link.

Goes inThe source code of the app and the recording from step 1
Comes outA map: screens, files, data requests, hidden links, sorted old tests and who changes what
It must
  • Explain each data request in the recording. Point to the code that makes it.
  • Sort the existing tests: keep, rewrite or throw away. Give a reason for each.
  • Mark a file that several screens use as shared. Do not give it to one screen.
  • Read the common ways to write apps: JavaScript or TypeScript, old and new routing, and the usual ways to store and get data.
Step 3 — suggest the pieces

Group the files into pieces and give the reasons

The strongest clue is data, because screens that show the same data usually belong together. The tools start from the screens of the app and give each file to the screen that uses it. They then add the files that share the data of a screen. Each suggested piece gets a score for each clue, so that a reviewer can see why the line is in this place. The same rules always give the same answer, which lets people check and repeat the result.

ToolsDraft the pieces with fixed rules, so that the same evidence always gives the same draft. They also write an API description for each backend.
AgentCan make judgment calls such as a name, a merge, a split or the place of a file that the rules cannot place. Each call is a named edit that the tools check, and the agent is optional.
PeopleNothing to do in this step, because you review the result in step 4.
How it works
  1. Each screen that fills the main area starts a piece, and the files that only that screen uses join it.
  2. The files that only the entry of the app uses form the shell.
  3. A file that is left joins the piece that supplies at least half of the data that it reads.
  4. A file that many pieces use gets a suggestion: split it, copy it, replace it with one data helper for each piece, or remove it.
  5. The tools score each piece on six clues, so that a reviewer can see why a line is in this place.

Example. On the reference app, the rules put 26 of 27 files in the correct piece. The agent fixes the last file by moving the constants file to the console.

It must
  • Give each piece the reasons for it, not only a name.
  • Mark each hidden link as a risk to fix. A hidden link is where one piece reads the data of another piece.
  • Tell apart an app with one backend and an app that sends requests to several backends.
  • Check that the tools can build the plan. Each piece must pass the same checks as a piece that people make by hand.
Step 3, continued — data

Describe the data that each piece needs

Each new piece gets its own data helper, and a data helper needs an API description of each backend that it uses. Monoliths rarely have one, so the tools write one from the recording: each question that the app asked and each answer that it got. They then compare it with the code, so that questions that the recording missed still show. Each data helper receives only the questions of its piece, and the recorded answers serve as sample data for demonstrations.

It must
  • Describe only what the app asked, or was written to ask. Do not guess more.
  • Mark the description as written by the tools. Record the recorded request for each part.
  • Use the own description of the backend when there is one. Report where the two differ.
Step 4 — people approve

Publish to the workspace, then review, discuss and approve

Steps 1 to 3 produce a bundle of data: the recording, the map of the code and the plan. Apps and tools read this bundle, and the workspace is one such app. The engineer publishes the plan and its evidence to the workspace, and people then agree on the plan there.

The workspace runs on the machine of the engineer or as a hosted service, and the screen is the same in both. It shows the plan on the real screens with a coloured box around each piece. People read the evidence, merge, split and rename pieces, move files, and discuss the plan in comments and with the agent before they approve.

The workspace keeps no data of its own. Each action is a named action that the tools check at once, and everything that depends on it moves too. The changes of people return to the repository, where the tools check each one again. The plan file stays the only record, and it includes the comments, the questions and the approval.

The AI agent works in the same screen. A person can ask a question, for example "split hazards out of cargo", and the agent answers with suggested changes. The tools try each suggestion on a copy of the plan. They drop a suggestion that breaks the plan and show the reason, and they keep the other suggestions until a person accepts them. The agent is a hosted model. It uses the coder plugin of the platform and an API key that the engineer sets. Without a key, the rest of the workspace works in the same way.

ToolsShow the plan on the real screens, check every change at once and record the approval.
AgentAnswers a question with suggested changes that a person accepts or rejects, and this is optional.
PeopleShape the plan and approve it, which makes this the main step for a product owner.
How it works
  1. The engineer publishes the plan and the evidence to the workspace.
  2. You open the workspace and see each screen of the app with a box around each piece.
  3. You click a piece and see its data, its files and the reasons for its boundary.
  4. You change the plan by renaming a piece, merging two, splitting one or moving a file, and the tools check each change at once.
  5. You can ask the agent, for example "split hazards out of cargo". The tools try each suggestion on a copy, and you accept or reject it.
  6. You approve, and the tools record who approved, when, and which version. A later change to the pieces makes the approval out of date.

Example. You rename the shell to console and approve. The name changes in every chip, box and label, and the approval names that version.

Try the clickable prototype of the workspace. It uses example data and saves nothing, so you can see the actions, the checks and the approval before you install anything.

On the machine of the engineer, one command opens the workspace: decompose:workspace. A hosted workspace takes a published snapshot of the plan and the evidence, and the screen and the actions are the same. The workspace is also one of the pieces that the platform builds. It is a generated MFE with four screen areas (the map, shaping, the agent and approval) and its own data helper.

It must
  • Publish the plan and its evidence as one snapshot that names the version of the plan.
  • Show each suggested piece on at least one real screen, and warn about each piece that no screen shows.
  • Keep no data of its own, so that a reload, a second tab or a restart shows the same plan.
  • Change the plan only through the named actions. Refuse an invalid change and give the reason.
  • Keep the conversation with the decision by storing comments, questions and answers in the plan.
  • Hold each agent suggestion until a person accepts or rejects it, and show if the suggestion still works.
  • Record who approved, when, and the exact version of the plan. A later change to the pieces makes the approval out of date, and a comment does not.
  • Return the changes of people to the repository and check each change again.
  • Treat the approval of the plan as the decision, and do not build anything before it.
  • Make the review package without the internet. The Figma page has its own screenshots.
  • Work the same on the machine of the engineer and as a hosted service.
Figure 4 — Figma

Turn a running screen into an editable Figma design

Separately from the review boxes, the tools can turn any screen of a running app into an editable Figma design. The design is made of frames, text and shapes, and it is not a flat picture. Designers then start from what is live and not from an old mock-up. This works on any web app, whether it is split or not.

It must
  • Include only what you can see on the screen, including the content inside reusable web components.
  • Use Figma auto-layout only where it matches the page exactly, and keep the exact positions in other places.
  • Report what the tools could not copy. A gradient becomes a plain colour, only the first shadow stays, and video, canvas and embedded frames become labelled placeholders.
Steps 5 to 7 — build, move, switch over

Move one piece at a time while the monolith keeps running

The tools do not replace all pieces at once. They first wrap the whole monolith as one piece, so that the new shell shows it unchanged. Then, one screen area at a time, they point that area at its new piece instead of the monolith. After each switch, step 8 checks that nothing changed, and the tools undo a switch that fails.

ToolsGenerate the empty pieces, change one placement at a time, run the step 8 check, and undo a switch that fails.
AgentMakes the monolith run as one piece and moves the code and the tests into the new pieces, writing only into files that developers own.
PeopleReview and approve each pull request.
Step 5 · how it works
  1. The tools read the approved plan and generate an empty piece and a data helper for each area.
  2. An agent changes the build of the monolith, so that the monolith also runs as one piece in the new shell.
  3. The tools write a composition that places the monolith everywhere, so that users see no difference at first.

Example. After this step, the shell shows the monolith as before, and the new pieces exist but show nothing yet.

Step 6 · how it works
  1. For one area, the agent moves its screens into the new piece.
  2. The tests that are marked keep move with the screens, and the agent writes new tests for the tests that are marked rewrite.
  3. The agent never edits a generated file, and the tools run the checks of the repository on the result.

Example. The cargo screens move into the cargo piece, and the shell still shows the monolith.

Step 7 · how it works
  1. The tools change one rule in the composition, so that the rule places the new piece and not the monolith in one screen area.
  2. They run the step 8 check against the recording.
  3. If the check passes, the change goes into its own pull request and a person approves it. If the check fails, the tools undo that one switch.

Example. The cargo manifest area now shows the cargo piece, and users see the same screen.

Step 5 · buildAn empty piece and data helper for each area in the plan, and the monolith as one piece. At first, each screen still shows the monolith.
Step 6 · moveThe code of each screen and the tests that are marked keep move into its piece. Tests that are marked rewrite get new tests that check behavior.
Step 7 · switch overOne screen area at a time moves from the monolith to its new piece. Each switch is its own small change for review.
It must
  • Keep the product working at all times, so that users see no difference during the work.
  • Never switch more than one screen area without a pass of the step 8 check.
  • Write only into the parts of each piece that developers own, and never write over files that the platform generates.
Figure 5 — step 8, check nothing changed

Replay the journeys and compare the results

The check takes the recording from step 1 and replays its journeys against the new version. It uses the same frozen clock and the same recorded answers, so that the data cannot differ. It compares the two runs screen by screen. The check first runs against the monolith, which proves that the journeys give the same result each time. After that, any difference means that the app changed.

ToolsReplay the journeys and compare, so that the same journeys and the same data give the same verdict.
PeopleSign off at the end.
How it works
  1. The tools run the check on the monolith alone first, and it must pass against itself.
  2. They replay the journeys of step 1 against the new version, with the same frozen clock and the same recorded answers.
  3. On each screen they compare four things: what is shown, which data is asked for, new errors, and how it looks.
  4. They write a report that says the same, or says exactly what changed and in which screen area.

Example. On the reference app, a change of one heading colour fails every step, and the report names the area that drew it.

It must
  • Pass against the monolith itself before it judges a new version.
  • Report a change once, in the screen area that caused it, and not in each area around it.
  • Allow no visual difference unless a person sets an allowance on purpose.
  • Name what the journeys never visited, so that nobody mistakes "not checked" for "unchanged".

What the evidence does not show

Limits of the evidence
  • The evidence covers steps 1 to 4 and step 8.
  • The two outside apps are versions of one product, so they show breadth of technology more than breadth of products.
  • The thresholds of the draft were tuned on the reference app, and the rules for test verdicts were written with its answer key in view. Only a second subject can show that they generalize.
  • A parity pass covers only the behavior that the journeys use, and the report lists the routes that no journey visits.
  • Fonts and rendering differ between machines, so capture the baseline on the machine that runs the check.
  • The hosted-model agent has not been measured for answer quality. The tools check each of its edits in the same way, whatever the quality.
Finding your way

Find the current step and the next command

Eight steps and a dozen commands are much to remember. The first run against the reference app took five wrong turns before a plan existed. One command now reads the evidence folder. It shows which steps are done, which are out of date because an earlier step changed, and which wait for a person. It also gives the exact next command, with the address and folder of the app already filled in. 

$ seans-mfe-tool flow:status ./evidence

  ✓ Run the app and record what it does
  ✓ Read the app's source, joined to the capture
  ✓ Propose the domains
  ○ Shape the proposal — merge, split, rename, ask the agent — 1 suggestion waiting
  ↻ Write the review package — proposal/decomposition.yaml changed since proposal/PROPOSAL.md was built
  ✓ Approve the proposal — approved by Sean

  next: seans-mfe-tool decompose:present ./evidence/proposal

The command keeps no record and reads the files on disk each time. Each step stores the versions of the inputs that it used, so "out of date" means that the inputs really changed. A change of branch changes only file dates and cannot cause it. The order of the steps is written once, as data, in flows/decompose.yaml (PDR-012, ADR-119).

PDR-011 and PDR-012 give the product reasons. ADR-109 to ADR-113 and ADR-115 to ADR-120 give the design reasons. They are in docs/architecture-decisions/. The reference app is examples/meridian-monolith/. The step-by-step guide is docs/decompose-runbook.md. See also Generator CLI Schematics, Runtime Platform Schematics and the system map.

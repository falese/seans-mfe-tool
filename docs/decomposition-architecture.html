seans-mfe-tool · how it works

Decomposing a monolith

Many products start as a monolith: one codebase that one team builds. As more teams change it, they block each other. These tools split the monolith into smaller pieces. Each team owns, changes and releases its own piece. Users see no difference.

This page explains each step and the rules that the step must follow.

Before you start

Terms

Monolith
The existing application that you decompose. It is one codebase that ships as one unit.
Piece
A bounded part of the product that one team owns, changes and releases on its own, for example orders or profile. It ships as one micro-frontend (MFE). The plan and the workspace call it a domain.
Shell
The host application that composes the pieces. It has the header, the navigation and the space where each piece renders.
Screen area
A rendered part of a screen, for example a table, a panel or a card. The capture records it as a region.
Backend
A service that supplies data to the screens.
Data helper
A small service for one piece. It gets the data of that piece from the backends and returns it in one consistent shape. It is a backend for frontend (BFF).
API description
A machine-readable list of what a backend accepts and returns, in OpenAPI format.
The plan
One file, decomposition.yaml. It lists the proposed pieces and the evidence for each. The tools derive everything else from it.
The workspace
The review screen for product owners. It shows the plan on the real screens. It changes the plan only through named actions. When a person approves, it records the exact version of the plan.
Figure 1 — the steps

Eight steps, and two approvals by people

The order is the order that a careful team follows by hand. First, find out what the app does. Next, decide where to cut it, and agree on the cuts. Then move one piece at a time. After each move, check that nothing changed. The tools find, suggest and check. People approve the cuts. People also approve the finished work.

Step 1 — watch the app

Use the app like a person would, and record everything

A browser opens the monolith. It follows short scripts that are called journeys. An example journey is: open the home page, click Docking, open a berth. The browser also explores the app alone and follows each link that it finds. At each step it records what is on the screen, which code drew each part, which data the screen asked for, and any errors. It also saves a screenshot.

Goes inThe running monolith, and optional journeys
What happensA browser clicks through the app. The clock is frozen, so dates do not change between runs
Comes outA recording: screens, screen areas, data requests and answers, errors and screenshots
It must
  • Name the code behind each screen area. Read the labels that React adds in development mode.
  • Link each data request to the screen area that shows the answer.
  • Keep each answer. Then the same journeys can run again with the same data and no live backend.
  • Never press buttons or send forms during exploration. Then the data of the app does not change.
  • Work with old and new apps. Support different React versions and both kinds of web address (/page and /#/page).
Step 2 — read the code

Find out what reaches what

The recording shows what happened. The code shows everything that can happen, also on screens that nobody visited. This step reads the code and makes a map. The map shows which address shows which screen, which files each screen uses, and which data each screen asks for. It follows each request to the backend address. It also finds data that a screen uses but does not show. This is a hidden link between areas. A screenshot cannot show it.

Goes inThe source code of the app, and the recording from step 1
What happensThe tools read the code and do not run it. Then they match the map to the recording
Comes outA map: screens, files, data requests, hidden links, sorted old tests, and who changes what
It must
  • Explain each data request in the recording. Point to the code that makes it.
  • Sort the existing tests: keep, rewrite or throw away. Give a reason for each.
  • Mark a file that several screens use as shared. Do not give it to one screen.
  • Read the common ways to write apps: JavaScript or TypeScript, old and new routing, and the usual ways to store and get data.
Step 3 — suggest the pieces

Group the files into pieces, and show the reasons

The strongest clue is data. Screens that show the same data usually belong together. The tools start from the screens of the app. They give each file to the screen that uses it. They add the files that share the data of a screen. Each suggested piece gets a score for each clue. A reviewer can see why the line is in this place. The same rules always give the same answer. This lets people check and repeat the result.

It must
  • Give each piece the reasons for it, not only a name.
  • Mark each hidden link as a risk to fix. A hidden link is where one piece reads the data of another piece.
  • Tell apart an app with one backend and an app that sends requests to several backends.
  • Check that the tools can build the plan. Each piece must pass the same checks as a piece that people make by hand.
Step 3, continued — data

Give each piece a description of the data it needs

Each new piece gets its own data helper. A data helper needs an API description of each backend that it uses. Monoliths rarely have one. So the tools write one from the recording. It has each question that the app asked and each answer that it got. Then the tools compare it with the code. In this way, questions that the recording missed still show. Each data helper gets only the questions of its piece. It also gets the recorded answers as sample data for demonstrations.

It must
  • Describe only what the app asked, or was written to ask. Do not guess more.
  • Mark the description as written by the tools. Record the recorded request for each part.
  • Use the own description of the backend when there is one. Report where the two differ.
Step 4 — people approve

Review the plan on the real screens

A plan that is a list is hard to judge. So the tools make a review package. It has a written summary. It also has each screen of the app with a coloured box around each suggested piece. The package is a web page and a Figma page. The reviewer can approve the plan. The reviewer can also rename, merge or split pieces, or move a file. Each change is a named action. So everything that depends on it moves too. The tools check the plan again immediately.

It must
  • Show each suggested piece on at least one real screen. Warn about each piece that no screen shows.
  • Keep the plan valid after each change. Refuse an invalid change and give the reason.
  • Work without the internet. The Figma page has its own screenshots.
  • Treat the approval of the plan as the decision. Do not build anything before it.

The workspace: the same review, for product owners

A product owner must not need to read a plan file or open a terminal. The workspace is a screen that shows the plan on the real app, as below. The owner can merge or split pieces, rename them, move a file, add comments and approve. The workspace keeps no data of its own. Each click is one of the same named actions, so the tools check it in the same way. The plan file stays the only record.

The AI agent also works there. A person can ask a question, for example "split hazards out of cargo". The agent answers with suggested changes. The tools try each suggestion on a copy of the plan. If a suggestion breaks the plan, the tools drop it and show the reason. The other suggestions wait until a person accepts them. The agent is a hosted model. It uses the coder plugin of the platform and an API key that the engineer sets. Without a key, the rest of the workspace works in the same way.

Try a clickable prototype of the workspace. It has example data and saves nothing. Use it to see the actions, the checks and the approval before you install anything.

An engineer opens the workspace with one command: decompose:workspace. It runs on the own machine of that person. It is also one of the pieces that the platform builds. It is a generated MFE with four screen areas (the map, shaping, the agent and approval) and its own data helper.

The workspace must
  • Keep no data of its own. After a reload, in a second tab or after a restart, it shows the same plan.
  • Change the plan only through the named actions. Refuse an invalid change and give the reason.
  • Hold each agent suggestion until a person accepts or rejects it. Show if the suggestion still works.
  • Record who approved, when, and the exact version of the plan. A later change to the pieces makes the approval out of date. A comment does not.
  • Run on the own machine of the person.
Figure 4 — Figma

Turn any running screen into an editable Figma design

The tools can also turn any screen of a running app into an editable Figma design. This is separate from the review boxes. The design has frames, text and shapes. It is not a flat picture. Designers start from what is live and not from an old mock-up. It works on any web app, split or not.

It must
  • Include only what you can see on the screen. Include the content inside reusable web components.
  • Use Figma auto-layout only where it matches the page exactly. In other places, keep the exact positions.
  • Report what the tools could not copy. A gradient becomes a plain colour. Only the first shadow stays. Video, canvas and embedded frames become labelled placeholders.
Steps 5 to 7 — build, move, switch over

Move one piece at a time, with the monolith still running

The tools do not replace all pieces at once. First, they wrap the whole monolith as one piece. The new shell then shows it unchanged. Then, one screen area at a time, the tools point that area at its new piece and not at the monolith. After each switch, step 8 checks that nothing changed. If something changed, the tools undo that one switch.

Step 5 · buildAn empty piece and data helper for each area in the plan. The monolith is also one piece. At first, each screen still shows the monolith.
Step 6 · moveThe code of each screen and the tests that are marked keep move into its piece. Tests that are marked rewrite get new tests that check behaviour.
Step 7 · switch overOne screen area at a time moves from the monolith to its new piece. Each switch is its own small change for review.
It must
  • Keep the product working at all times. Users must see no difference during the work.
  • Never switch more than one screen area without a pass of the step 8 check.
  • Write only into the parts of each piece that developers own. Never write over files that the platform generates.
Figure 5 — step 8, check nothing changed

Replay the same journeys and compare

The check takes the recording from step 1. It replays the journeys against the new version. It uses the same frozen clock and the same recorded answers, so the data cannot differ. It compares the two runs screen by screen. First, run it against the monolith. This proves that the journeys give the same result each time. After that, any difference means that the app changed.

It must
  • Pass against the monolith itself before it judges a new version.
  • Report a change once, in the screen area that caused it. Do not report it in each area around it.
  • Allow no visual difference unless a person sets an allowance on purpose.
  • Name what the journeys never visited. Then nobody mistakes "not checked" for "unchanged".
Does it work?

Tested on our own app, and on two apps that we did not write

The short answer On our reference app, which we built to split, the tools found the seven planned pieces. They also tested two unrelated public versions of the same blogging product. Different people wrote them with different tools. The tools found the same eight pieces in both. The tools explained each data request in both. Both passed the step 8 check against themselves. The two outside apps showed sixteen gaps that the reference app could not show. We fixed all sixteen.
Finding your way

Ask where you are, and get the next command

Eight steps and a dozen commands are much to remember. On the first run against the reference app, a user made five wrong turns before a plan. Now one command reads the evidence folder. It shows which steps are done and which are out of date because an earlier step changed. It shows which steps wait for a person. It also gives the exact next command, with the address and folder of the app already filled in. 

$ seans-mfe-tool flow:status ./evidence

  ✓ Run the app and record what it does
  ✓ Read the app's source, joined to the capture
  ✓ Propose the domains
  ○ Shape the proposal — merge, split, rename, ask the agent — 1 suggestion waiting
  ↻ Write the review package — proposal/decomposition.yaml changed since proposal/PROPOSAL.md was built
  ✓ Approve the proposal — approved by Sean

  next: seans-mfe-tool decompose:present ./evidence/proposal

The command keeps no record. Each time, it reads the files on disk. Each step stores the versions of the inputs that it used. So "out of date" means that the inputs really changed. A change of branch changes only file dates and cannot cause it. The order of the steps is written once, as data, in flows/decompose.yaml (PDR-012, ADR-119).

PDR-011 and PDR-012 give the product reasons. ADR-109 to ADR-113 and ADR-115 to ADR-119 give the design reasons. They are in docs/architecture-decisions/. The reference app is examples/meridian-monolith/. The step-by-step guide is docs/decompose-runbook.md. See also Generator CLI Schematics, Runtime Platform Schematics and the system map.

Monolith Decomposition Schematics

How the toolchain takes a monolithic React app apart into independently deployable capabilities. It watches the running app, reads its source, and proposes domains with the evidence behind each one. A person agrees the boundaries. A parity gate then proves the result still behaves like the original. Six drawings, then the results on an app we wrote and on two apps nobody here wrote.

The product decision is PDR-011, and the architecture is ADR-109 to ADR-113, in docs/architecture-decisions/. The reference subject is examples/meridian-monolith/. Every stage below is a CLI command, so an agent reaches it the way a person does (as an MCP tool). Companion to Generator CLI Schematics and Runtime Platform Schematics, which describe what the decomposition produces.

Figure 1 — the pipeline

Eight stages, two human gates

A monolith is taken apart in the order a careful team would do it by hand: find out what it does, decide where the seams are, agree them, then move one piece at a time, proving after each move that nothing changed. The toolchain does the finding, proposing and proving. People make the two decisions that are theirs.

Figure 2 — evidence

What the app did, joined to what the code says

Neither signal is enough on its own. The running app shows which data appears in which part of the screen. The source shows what reaches what, including behaviour no journey happened to exercise. The bridge between them is React's development metadata. Every element on the screen knows which component drew it and which file that component is in, so both halves talk about the same units.

Figure 3 — agreement

One document is agreed; everything else is derived from it

The proposal is a single reviewable file, decomposition.yaml. It records the domains, the files and capabilities each owns, the backends each fronts, the slots and routes that compose them, the shared files, the couplings, and the test triage. People and the agent edit that file and nothing else. The manifests, the composition and each BFF's API spec are re-derived from it and re-validated on every change.

Figure 4 — API specs nobody wrote

Each BFF gets a spec inferred from what the app actually called

Every generated BFF needs an OpenAPI document for each backend it fronts, and a monolith's backends rarely have one. So one is inferred from the recorded traffic and the endpoint templates in the client code. It is a lower bound: only what the app was seen or written to call. It is marked as inferred, and each operation names the requests it came from. Where a backend publishes a real spec, the real one wins and the inferred one reports how they differ.

Figure 5 — the parity gate

Proof that a step changed nothing

decompose:verify drives a candidate through the baseline's journeys, with the same frozen clock and the same recorded responses, and compares the two runs step by step. Run against the monolith itself first, it proves the journeys are repeatable. After that, any difference means the app changed.

Figure 6 — results

On an app we wrote, and on two apps nobody here wrote

meridian-monolith is the reference subject: seven domains in one React app, written the way real teams write them, with a deliberately poor test suite and an answer key. Scores against an app we wrote only show agreement with us. So the toolchain was also run on two independent implementations of RealWorld (“Conduit”), one product built in dozens of frontends against one published API spec. Same product, so the same domains should come out. Published spec, so every inferred API has a ground truth.

Why the corpus matters On its first run against code nobody here wrote, the toolchain found almost nothing: no routes and no endpoints in one app, and everything collapsed into a single domain in both. Sixteen gaps came to light that the reference app, written to suit the tool, never could. Among them: React 16, hash routing, routes in plain JavaScript, a central Redux store that made every page look shared, and a single API mistaken for many backends. All sixteen are fixed, and the reference app's scores did not move.

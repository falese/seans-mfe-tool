# Schemas and Contracts — how a published contract is derived

**Status:** Explanatory. Describes the machinery that produces every published
contract in this repository, and what that machinery does and does not
guarantee.

**Citations.** Symbols, not line numbers — this page is prose, so nothing
derives it and nothing gates it, and a line number is the part most likely to
be wrong by the time you read it. The irony is the subject of §7.

**Scope.** This is about *derivation* — where a contract comes from and what
keeps it true. For the shape of the CLI envelope and its exit codes, see
[`cli-contract.md`](./cli-contract.md); for what the manifest language accepts
field by field, see [`schemas/manifest-fields.md`](./schemas/manifest-fields.md)
(itself generated by the machinery described here).

---

## 1. The problem this system exists to solve

`seans-mfe-tool` is three things at once:

| It is | Its contract is read by |
|---|---|
| a CLI a person types | a developer reading `--help` |
| a library another package imports | a compiler resolving types |
| a tool surface an agent calls | an MCP client validating JSON |

All three need to know the same facts — what a command accepts, what it
returns, what a manifest may contain. The cheap way to serve three audiences is
to write the answer three times. That is also the way it ends up wrong in at
least one of them, silently, because nothing compares the copies.

The measured cost of doing it the cheap way, in this repository:

- `build:*` had no schema entry at all, so an agent could scaffold and validate
  an MFE over MCP but never build one.
- `deploy` advertised eight flags the command did not have. Any agent using
  them got a hard parse failure.
- `remote:generate` returned a `preserved` field absent from a schema declared
  `additionalProperties: false`, so a **validating** client rejected every
  successful response. Same for `bff:validate`'s `manifest` and `meshConfig`.
- Four documents described the manifest language. The one titled *"the complete
  platform contract that ALL MFEs must conform to"* was the most stale of them
  — it did not know the slot contract existed.
- Two packages read the same `manifest.transforms` field against two different
  tables: `transforms: [filterSchema]` was rejected by the DSL validator and
  accepted by codegen; `transforms: [filter-schema]` was the reverse. Whichever
  spelling an author picked, half the platform objected.

### The rule

> **Every published contract is derived from the code that already enforces it,
> and a gate fails when the committed artifact disagrees.**

Not "documented next to". Not "kept in sync by a checklist". *Derived* — so the
artifact cannot say something the implementation does not, because nobody is
writing the artifact.

This is the same rule ADR-075 applied to the ADR index and ADR-065 applied to
the API reference, generalised: **generate the page the reader is least able to
verify.** A reader can check a code sample by running it. They cannot check a
JSON Schema without the source of truth in front of them — which is exactly the
situation where a wrong one survives longest.

## 2. The components

| Component | Owns | Path |
|---|---|---|
| **`@seans-mfe/contracts`** | Shared vocabulary at the root of the dependency graph: the envelope type, exit codes, the typed error hierarchy, the platform capability set, the Mesh table, the slot grammar | `packages/contracts/src/` |
| **`CommandResult<T>` + `EXIT_CODES`** | The envelope every command emits and the numeric codes it exits with | `packages/contracts/src/envelope.ts` |
| **`BaseCommand<T>`** | The inversion that makes the output contract knowable: subclasses implement `runCommand(): Promise<T>`, never `run()` | `packages/oclif-base/src/BaseCommand.ts` |
| **`DSLManifestSchema`** | The manifest language itself, in Zod — the only definition of what `mfe-manifest.yaml` accepts | `packages/dsl/src/schema.ts` |
| **Input derivation** | Turns a command's own flag and arg declarations into an input schema; decides which commands are agent-facing at all | `src/oclif/schema-derivation.ts` |
| **Output derivation** | Turns a TypeScript type into JSON Schema, and finds the `T` in `extends BaseCommand<T>` | `src/oclif/type-to-schema.ts` |
| **Command-lane driver** | Loads the live oclif registry, runs both halves, writes or diffs `schemas/<cmd>.json` | `scripts/generate-schemas.ts` |
| **Manifest-lane driver** | Runs Zod's own JSON Schema emitter over the manifest and composition schemas | `scripts/generate-dsl-schema.ts` |
| **Field reference generator** | Turns the generated manifest schema into the human-readable field table | `scripts/generate-manifest-reference.ts` |
| **The artifacts** | 20 per-command contracts + 2 document schemas. Committed, gated, never hand-edited | `schemas/` |
| **The consumer** | Reads `schemas/` and turns each contract into an agent-callable tool | `src/mcp/tool-registry.ts`, `src/mcp/sources/local.ts` |

### Two lanes

The system has exactly two derivation lanes. They share the rule and share
nothing else — different sources, different mechanisms, different artifacts.

```
LANE A — the command contract
                                                     ┌──────────────────┐
  command class                                      │ schemas/         │
  ├─ static flags / args ──► deriveInputSchema ─────► │   <cmd>.json     │
  │                          (live oclif registry)    │   .input         │
  │                                                   │   .output        │
  └─ extends BaseCommand<T> ► resolveCommandResultType│   .errorCodes    │
                              └► typeToJsonSchema ───►└────────┬─────────┘
                                 (TypeScript checker)          │
                                                               ▼
                                                       MCP tool catalogue
                                                       (what an agent may call)

LANE B — the manifest contract
                             ┌──► z.infer ──────────► the generator's typed manifest
  packages/dsl/src/schema.ts │
  (Zod — source of truth) ───┤                        ┌─────────────────────────┐
                             └──► z.toJSONSchema ───► │ schemas/dsl/            │
                                                      │   manifest.schema.json  │
                                                      └───────────┬─────────────┘
                                                                  │
                                       editor validation ◄────────┤
                                                                  ▼
                                                     docs/schemas/manifest-fields.md
```

## 3. Deep dive — Lane A, the command contract

### 3.1 Selection: which commands become a contract at all

`scripts/generate-schemas.ts` starts from `Config.load(REPO_ROOT)` — **the same
resolution the CLI itself performs at startup**, first-party plugins included.
That choice matters more than it looks: the catalogue cannot describe a command
set the CLI does not actually have, because it is asking the dispatcher, not
parsing source or reading a list.

`selectCatalogCommands` then applies four filters
(`src/oclif/schema-derivation.ts`):

| Filter | Why |
|---|---|
| `!hidden` | oclif's own signal that a command is not public |
| `!isAliasEntry` | oclif lists an alias as its own registry entry, distinguishable *only* by its id appearing in its own `aliases` array. Without this, `adr:doctor` and `mfe:doctor` each produce a duplicate tool for a command already catalogued |
| `isFirstParty` | `seans-mfe-tool`, `@seans-mfe/*`, `@falese/*`. Everything else is infrastructure that happens to be installed |
| `!(id in CATALOG_EXCLUDED)` | Two entries, each with a written reason |

`CATALOG_EXCLUDED` is deliberately two lines long, and its comment says why:
*"deliberately not a place to park real gaps."* `mcp:serve` is excluded because
advertising it would offer an agent a tool that starts another copy of the
server it is talking to. `schemas` is excluded because it lists the catalogue,
which the agent gets from `tools/list` anyway. **`build:*` is absent from the
exclusion list on purpose** — its absence from the catalogue was the original
defect this module exists to close.

### 3.2 The input half

`deriveInputSchema` (`schema-derivation.ts`) walks the command's own
declarations. Args first, because declaration order *is* argv order; then flags.

Three details worth knowing:

**`TRANSPORT_OWNED` is subtractive, not decorative.** `json`, `interactive` and
`cwd` are stripped from every input schema. `--json` is appended to every child
invocation by the MCP transport and the envelope contract depends on it, so
letting a caller set it is a way to *break* the response rather than a
capability. `cwd` is the reserved execution argument the registry injects on
every tool — it must not also arrive as a command flag.

**`x-positional` preserves what JSON Schema cannot express.** A JSON object has
no order, but argv does. The extension records which properties are positional
args and in what order, so the MCP transport can reassemble a real command line
from a flat object.

**Flag types map narrowly.** `boolean` → `{type: 'boolean'}`; `multiple` →
an array, with `enum` on the items if the flag declares `options`; otherwise a
string with an optional `enum`. `description` and `default` carry through
verbatim — which is why editing a flag's help text changes the published
contract, a property revisited in §6.

### 3.3 The output half — this is the interesting part

A command's result type is a *TypeScript* artifact. It does not exist at
runtime; there is nothing to introspect. So this lane does not run the
command — it runs the compiler.

**Step 1 — find the type.** `resolveCommandResultType`
(`type-to-schema.ts`) walks the source file's top-level children looking for
a class declaration that is a default export, then its `extends` heritage
clause, then a type argument on `BaseCommand`:

```ts
export default class MfeValidate extends BaseCommand<MfeValidateResult> {
//                                       ─────────── ─────────────────
//                                       matched      the T that is extracted
```

`checker.getTypeFromTypeNode(arg)` turns that syntax node into a real
`ts.Type`. A command with no type argument, or `BaseCommand<void>`, yields
`undefined` — and §3.5 explains why that is a hard failure rather than an empty
schema.

**Step 2 — convert the type.** `typeToJsonSchema` walks it. The conversion is
deliberately narrow, and the module comment states the reason: *"a type too
complex to express is a signal about the result type, not a reason to widen
this."*

| TypeScript | JSON Schema | Note |
|---|---|---|
| `string`, `number`, `boolean`, `null` | the obvious | |
| `unknown`, `any` | `{}` | constrains nothing, says nothing |
| `object` (bare keyword) | `{type: 'object'}` | TS flags this `NonPrimitive`, not `Object` — an easy miss |
| `'a' \| 'b'` | `{type: 'string', enum: ['a','b']}` | |
| `string \| null` | `{type: ['null','string']}` | **sorted**, because TS does not guarantee union member order and these files are under a byte-for-byte gate |
| `T[]` | `{type:'array', items: …}` | |
| `a?: string` | `string`, and `a` omitted from `required` | TS models this as `string \| undefined`; optionality belongs in `required`, not in the member schema |
| `boolean` in a union | collapsed | TS models `boolean` as `true \| false` |
| a union of object shapes | `{}` | would need `oneOf`; no command result uses one, and guessing is worse than silence |
| an object with no enumerable members | `{type: 'object'}` | `Record<string, unknown>` and friends: say "an object" rather than invent a closed shape that rejects valid data |

Recursion is bounded by `MAX_DEPTH = 12` and a `seen` set, so a self-referential
type terminates instead of hanging the build.

**Step 3 — lift the prose.** Inside `convertObject`, for every property:

```ts
const description = ts
  .displayPartsToString(prop.getDocumentationComment(checker))
  .trim();
if (description) schema.description = description;
```

The JSDoc written to explain a field *to a human reading the TypeScript*
becomes the `description` *an agent reads when deciding whether to call the
tool*. One sentence, two audiences, no synchronisation step and no second place
to forget. This is the single highest-leverage line in the system.

**Step 4 — inherit.** `checker.getPropertiesOfType` flattens inheritance, so a
field from `MutatingResult` (`dryRun`, `plannedChanges`) lands in the schema
beside the command's own. A command cannot publish a narrower envelope than it
actually returns by forgetting that it extends something.

**Step 5 — close the object, carefully.** `additionalProperties: false` is what
makes a future undeclared field fail loudly rather than silently break
validating clients. But `additionalPropertiesFor` checks for a string index
signature first:

```ts
const indexInfo = checker.getIndexInfoOfType(type, ts.IndexKind.String);
if (!indexInfo) return false;
```

A type declaring `[key: string]: unknown` says extra keys are legal. Closing it
anyway would publish a schema **stricter than the type it claims to describe** —
which is precisely how `bff:validate`'s `manifest` field came to be rejected by
its own published contract.

### 3.4 One compiler option, pinned on purpose

`deriveOutputSchemas` builds its `ts.Program` from the repo `tsconfig.json` but
overrides three options. Two are obvious (`noEmit`, `skipLibCheck`). The third
is not:

```ts
strictNullChecks: true,
```

It is redundant today, because the repo compiles strict — and it is kept
deliberately, because it was *not* redundant when written. Under the previous
`strict: false`, `string | null` collapsed to `string`, and the published schema
claimed `EnvCheckResult.found` was always a string while `build:check` really
returns `null` for a missing tool. Pinning it here means the published contract
stays true to the authored types no matter what the repo's compiler settings do
later. The contract's fidelity does not depend on an unrelated config file.

### 3.5 Assembly, and two failure modes made loud

Each contract is assembled as:

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id":     "https://seans-mfe.dev/schemas/<id>.json",
  "title":   "<command id>",
  "description": "<the command's own description>",
  "input":   { … },
  "output":  { … },
  "errorCodes": { "ok": 0, "usage": 2, "validation": 64, … }
}
```

`errorCodes` is spread from `EXIT_CODES` in `@seans-mfe/contracts` rather than
restated, so adding an exit code cannot leave the schemas stale.

**A command with no derivable output type is a build failure, not an empty
schema.** `buildSchema` throws with a message naming the two legitimate
resolutions — give the command a typed result, or add it to `CATALOG_EXCLUDED`
with a reason. Emitting `{}` would have been the quiet option and would have
published a contract that promises nothing.

**Filenames must round-trip.** `topic:command` becomes `topic-command.json`, and
every consumer — the JSON contract tests, the command-conformance tests, and
both MCP tool sources — recovers the id by turning every `-` back into a `:`. So
a hyphen anywhere in a command id is ambiguous: `control-plane:build` would land
in `control-plane-build.json` and come back as `control:plane:build`, matching
no command and failing three unrelated suites with no mention of the cause.
`schemaFilename` throws at generation time instead, where the fix is obvious.

**Orphans are removed, not ignored.** After writing, the driver lists
`schemas/*.json` and deletes (or, in check mode, reports) any file with no
corresponding command. A schema that outlives its command keeps advertising a
tool that cannot run.

## 4. Deep dive — Lane B, the manifest contract

Lane B is shorter because Zod does the work. `packages/dsl/src/schema.ts` is the
source of truth and feeds two consumers by two different mechanisms:

**`z.infer` → the compiler.** `DSLManifest` is inferred from the schema, never
declared beside it. The generator receives a manifest that is *already* typed
and *already* validated; there is no second definition to drift.

**`z.toJSONSchema` → the artifact.** `scripts/generate-dsl-schema.ts` emits
`schemas/dsl/manifest.schema.json` and, by the same contract,
`schemas/dsl/control-plane.schema.json` for the composition document (ADR-083).

One option is load-bearing:

```ts
z.toJSONSchema(DSLManifestSchema, {
  target: 'draft-2020-12',
  unrepresentable: 'any',
})
```

The manifest language is deliberately open in places — `framework` and
`bundler` are `z.string().min(1)` rather than enums (ADR-036), authorization is
deferred (ADR-007). `unrepresentable: 'any'` renders those permissively instead
of failing generation. Being *unable to express* an open field is not a reason
to close it.

Both documents are emitted before the script exits, so `--check` reports every
stale file in one run rather than making the caller rediscover them one at a
time.

**And then the docs.** `scripts/generate-manifest-reference.ts` reads the
*generated* JSON Schema — not the Zod source — and renders
`docs/schemas/manifest-fields.md`. Field descriptions come from `.describe()`
calls on the Zod fields themselves, so the same sentence serves the schema, the
editor tooltip, and the reference page. This is Lane A's JSDoc trick in a
different notation.

## 5. What an agent actually sees

`src/mcp/sources/local.ts` walks `schemas/`, one level deep, and turns each file
into a tool: `bff-init.json` → `mfe:bff:init`, with `schema.input` as the
`inputSchema` and `schema.description` as the description.

It filters on `isCommandContract` — the presence of an `input` key. `schemas/`
holds two kinds of file: per-command contracts and standalone document schemas
like `manifest.schema.json`. Only the former map to a runnable command, so only
the former become tools; otherwise an agent is offered a tool whose call can
only ever fail.

`loadToolRegistry` then merges three sources — local, installed oclif plugins,
and remote servers from `~/.config/seans-mfe/mcp.json` — and **aborts startup on
a name collision** rather than letting one source silently shadow another.

Every tool additionally accepts a reserved `cwd`, injected by the registry,
which is why `cwd` is in `TRANSPORT_OWNED` back in §3.2. The two ends of that
rule are 200 lines apart in different packages; they agree because one is
written as the reason for the other.

## 6. The gates

Derivation without a gate is a convention. These are what make it a contract.

| Gate | Catches | Where |
|---|---|---|
| `npm run build` then `git diff --exit-code schemas/` | Committed command contracts disagreeing with a fresh derivation | `.github/workflows/test.yml` |
| `npm run build:schema:dsl:check` | A stale `manifest.schema.json` — `providesSlots` shipped 2026-07-11 and was missing from the artifact for months because this check existed but was never wired in | `test.yml`, ADR-073 §6 |
| `npm run build:manifest-reference:check` | A stale field reference | `test.yml` |
| `npm run build:docs` + `git diff docs/api` | A stale TypeDoc API reference | `.github/workflows/api-docs.yml`, ADR-065 |
| `output-schema-conformance.test.ts` | What commands *actually return*, validated with ajv against what they publish | `src/oclif/__tests__/` |
| `command-conformance.test.ts` | Every catalogued command either exercised or excluded with a named reason | `src/oclif/__tests__/` |

The conformance test deserves a note, because it looks redundant and is not.
Output schemas are derived from the declared type, and TypeScript already
enforces that a command returns that type — so what is left to check? Its own
header answers: *"a belt over the compiler's braces."* It catches the gap the
type system cannot see — a runtime `as` cast, a hand-built object literal that
escapes the declared type, a field added by a helper. Cheap insurance on a link
that is otherwise sound.

Note also a small inconsistency, stated so nobody treats it as significant: the
command lane is gated by *write-then-diff* while the other lanes use a `--check`
mode. Both are real gates. `--check` produces a better message (it names the
stale file and the command to run); `git diff --exit-code` produces a diff.

## 7. What this guarantees — and what it does not

**Guaranteed.** The chain

```
implementation  →  declared type T  →  published schema  →  agent tool
```

cannot break anywhere along its length, with no runtime validation involved.
TypeScript enforces the first link; derivation produces the second and third
from that same `T`; the gate holds the committed artifact to it. The class of
bug where a published contract describes a shape the code does not produce is
structurally unreachable.

**Not guaranteed: that any of it is *true*.**

Derivation guarantees agreement between places. It does not guarantee agreement
with reality. This repository has a live demonstration:

> ADR-089 redefined `--force` from *does nothing* to *replaces developer-owned
> files*. `remote:generate:capability`'s flag description stayed
> `'Overwrite existing files'`. The pipeline faithfully republished that
> sentence into the published JSON Schema on every build, for months, where an
> agent read it as the tool's documentation. Everything was perfectly
> consistent the entire time it was wrong.

What caught it was a person reading the string against the decision record that
superseded it. No gate here can do that, because every gate compares an artifact
to a source — and the source itself was the thing that was wrong.

So the honest statement of what this system buys:

- It removes **transcription** error entirely.
- It does nothing about **authoring** error.
- Its main cost is that the second is now the *only* kind left, which makes it
  easier to find and easier to overlook.

A related instance, found while writing this page: the header of
`src/oclif/schema-derivation.ts` still claimed *"Output schemas stay
hand-authored: a command's TypeScript result type is not introspectable at
runtime."* That stopped being true when `type-to-schema.ts` landed. A module
comment is prose about the system, so nothing derives it and nothing gates it —
drift in the very module that exists to prevent drift.

## 8. Working with it

**Adding a command.** Declare `extends BaseCommand<TResult>` with a real result
interface and implement `runCommand()`. Run `npm run build:schemas`. If it
throws *"No output schema"*, the source file was not found by convention
(`topic:cmd` → `src/commands/topic/cmd.ts`) or the class has no type argument.
Commit the generated `schemas/<cmd>.json`.

**Changing a result type.** Add the field to the interface *with a JSDoc* — that
comment becomes the field's published description. Regenerate and commit.

**Changing a flag's help text.** That is a contract change: it reaches the
published schema and the agent-facing tool description. Regenerate and commit.

**Changing the manifest language.** Edit the Zod schema, including its
`.describe()`. Run `npm run build:schema:dsl && npm run build:manifest-reference`
and commit both artifacts.

**Never hand-edit** anything under `schemas/` or `docs/api`, or
`docs/schemas/manifest-fields.md`. Each carries a generated-file header, and
each has a gate that will reject the edit.

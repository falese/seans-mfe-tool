The generator in the build

Every MFE is described by one file, mfe-manifest.yaml. The generator turns that file into the platform layer of the MFE. This page shows when it runs, which GitHub Actions workflow runs it, and what each failing check means.

The short version

It runs first in every MFE build An MFE's build script is remote:generate, then the bundler, then the BFF build. The platform layer is rebuilt from the manifest each time. ADR-043
It splits files by owner Generator-owned files are rewritten on every run. Developer-owned files are written once and then left alone. ADR-082, ADR-091
CI proves both halves The Tests workflow regenerates every example MFE and fails on any difference. The Composition workflow builds them for real. test.yml, composition.yml

1. What runs in one MFE's build

A generated MFE carries this build script. Angular is the same with ng build in place of rspack build.

seans-mfe-tool remote:generate  &&  rspack build  &&  mesh build
                                                  (only if the manifest has a data: section)

Inside remote:generate

  1. Validate. The manifest is checked, including its mesh plugin and transform settings (ADR-027). A bad manifest stops here and nothing is written.
  2. Pick the framework. One rule reads framework/bundler or targets.web (ADR-092). If neither is set, you get React with rspack. The CLI loads the matching framework plugin and passes its variant to the generator (ADR-036, ADR-061).
  3. Plan. Capabilities are sorted into the platform ones and your own. Lifecycle hooks are collected in order. A hook with a source is wired through a generated handler registry instead of an empty stub (ADR-040).
  4. Render. The variant supplies a list of files to emit. Each entry names a template, an output path and an owner (ADR-093). Plugins can add entries, such as the BFF files (ADR-094).
  5. Write. Generator-owned files are written every time. A developer-owned file that already exists is skipped and listed as Kept. --force is the only way to overwrite one, and it prints each file it replaced (ADR-091).

Steps 1 to 4 never touch the disk. They return a list of files and a list of warnings. Only step 5 writes, and the CLI decides how to show the warnings.

3. The Tests workflow, step by step

The quality job runs on Node 20. It installs, lints, typechecks and builds, then runs these gates in this order. The five that run the generator are marked.

ADR, system map, contract and index checkscheck:adr and the :check buildsnoA generated document disagrees with the repository.
Meridian regen invariantexamples/meridian-station/scripts/generate.mjs --checkyesRe-running remote:generate across the Meridian fleet, plus its seeds, changes anything.
Template typecheckcheck:template-typecheckyesA freshly scaffolded MFE, with a real npm install, does not typecheck against the runtime's public exports.

Why drift and the snapshot are separate gates. The drift gate compares generated bytes to what is on disk, and only for generator-owned files. The snapshot gate compares everything the generator emits to a baseline file. A change to a developer-owned template, such as App.tsx.ejs, passes drift and fails the snapshot. That is the intent: you review it as part of the change.

The Swift and Rust jobs run in language containers because they need those toolchains and no Node. Each script is called with --require, so a missing toolchain fails the job. Without the flag the script skips and exits 0.

4. The Composition workflow

The Tests workflow checks files. This one checks that the files work together. It runs on Node 22 and finishes in this order:

  1. Build the CLI. npm run build, then npm run docker:build:cli. The compiled dist/ is baked into the CLI image.
  2. Build five services, one at a time. Registry, daemon, shell, meridian-console and abc-kids-flappy. Each image's build stage runs npm run build, which is where remote:generate runs again, using the CLI image. Building one at a time avoids the memory exhaustion that parallel builds cause.
  3. Start the stack and wait for each service to answer, up to five minutes each.
  4. Register rules.json with the registry.
  5. Drive the composition in Chromium with Playwright, across two applications.
  6. On failure, upload the report and container logs, kept for seven days. The stack is always torn down.

It is limited to paths that can change what gets built: templates, runtime, contracts, the React framework package, the control plane, the CLI Dockerfile, and the two example apps.

7. How this page reaches the site

The Publish docs site workflow owns the whole site. It does not run the generator. It builds the slide deck and the API reference when it can, then scripts/assemble-site.js copies each HTML page into _site/. scripts/check-site.js fails the build on a broken link or an external asset. A pull request uploads a 14-day preview artifact. A push to main deploys to GitHub Pages. This page is self-contained, with no external fonts, scripts or images, because that check rejects them.

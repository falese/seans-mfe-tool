The generator in the build

Every MFE is described by one file, mfe-manifest.yaml. The generator turns that file into the platform layer of the MFE, and it runs as the first step of the MFE's own build. Because of that, any CI system that builds an MFE runs the generator. This page says what a CI system must provide, gives a checked recipe, and then shows how this repository does it on GitHub Actions.

The short version

The build runs it An MFE's build script is remote:generate, then the bundler, then the BFF build. A CI job that runs npm run build has run the generator. ADR-043
It splits files by owner Generator-owned files are rewritten on every run. Developer-owned files are written once and then left alone. That split is what makes a CI check possible. ADR-082, ADR-091
The checks are commands Every gate is a CLI or npm run command with an exit code. GitHub Actions only decides when to run them. Portable by design

1. What runs in one MFE's build

A generated MFE carries this build script. Angular is the same with ng build in place of rspack build.

seans-mfe-tool remote:generate  &&  rspack build  &&  mesh build
                                                  (only if the manifest has a data: section)

Inside remote:generate

  1. Validate. The manifest is checked, including its mesh plugin and transform settings (ADR-027). A bad manifest stops here and nothing is written.
  2. Pick the framework. One rule reads framework/bundler or targets.web (ADR-092). If neither is set, you get React with rspack. The CLI loads the matching framework plugin and passes its variant to the generator (ADR-036, ADR-061).
  3. Plan. Capabilities are sorted into the platform ones and your own. Lifecycle hooks are collected in order. A hook with a source is wired through a generated handler registry instead of an empty stub (ADR-040).
  4. Render. The variant supplies a list of files to emit. Each entry names a template, an output path and an owner (ADR-093). Plugins can add entries, such as the BFF files (ADR-094).
  5. Write. Generator-owned files are written every time. A developer-owned file that already exists is skipped and listed as Kept. --force is the only way to overwrite one, and it prints each file it replaced (ADR-091).

Steps 1 to 4 never touch the disk. They return a list of files and a list of warnings. Only step 5 writes.

2. What any CI system must provide

The generator is a command-line program. It has no CI-specific code and reads no CI environment variables. These are the requirements, and nothing else is needed.

NeedDetail
Node and npmThe CLI declares Node 20 or newer and npm 10 or newer in its engines field.
The CLI on PATHThe build script calls seans-mfe-tool by name, and the generated package.json does not install it. Your CI image or an earlier step must. In this repo the Docker images carry it. This is the one prerequisite that is easy to miss.
A checkout with the manifestRun from the MFE's directory. Outside one, remote:generate exits 64.
No install for generationremote:generate needs the CLI, not the MFE's own node_modules. The bundler step does need npm ci.
Toolchains for native targetsOnly if the manifest declares targets.swift or targets.rust, and only to build and test those outputs.

Exit codes are plain: zero is success. Under --json a command prints exactly one result object on stdout and everything else goes to stderr, so a pipeline can parse it. A failed mfe:validate exits 65, and the object names each problem's rule, file, line and fix.

3. The portable recipe

This runs in any CI that can run shell commands. The sequence has two checks because they see different failures, as the results below show.

# run from the MFE's directory, on a clean checkout
seans-mfe-tool mfe:validate           # is the MFE internally consistent?
seans-mfe-tool remote:generate        # rewrite generator-owned files only
git diff --exit-code                  # did that change anything committed?
npm ci && npm run build               # then build as usual

Checked against a fresh scaffold

These results come from running the recipe on an MFE made with remote:init demo --host meridian, generated once and committed, using the CLI from a local build of this repository. Each row changes one thing and records the exit codes.

Scenariomfe:validateremote:generategit diff --exit-codeMeaning
Clean scaffold, regenerated000Generation is repeatable. Nothing changes.
A hand edit to a generator-owned file, committed001Only the diff step catches it. Generation silently restored the file, and the diff shows the one line it removed.
Manifest changed, platform files not regenerated001The diff shows the stale bootstrap.ts and mfe.test.ts.
A manifest dependency removed from package.json650n/aOnly validate catches it. package.json is developer-owned, so generation leaves it alone. Validate reported 4 problems.

Keep both checks. mfe:validate alone misses a hand edit to a platform file. The generate-and-diff pair alone misses a bad dependency version. The platform repo runs the same pairing at fleet scale as check:mfe-drift:check and check:mfe-consistency.

Not covered by this check. It ran with the CLI from a local build, not from a package installed from a registry. The publish-shape gate below covers packaging. A developer-owned file that has fallen behind a platform change is reported as a migration warning in the validate output (ADR-082). Warnings do not fail the run, so read the summary line.

The platform repo runs more gates than a consumer needs. Each is a command, so each can move to any CI. "When" is the reason to run it, not a GitHub trigger.

Always pass --require to the native gates in CI. Without it each script skips with a notice when its toolchain is missing, and exits 0. That is right on a laptop and wrong in a pipeline, where a skipped gate looks like a passed one.

Why drift and the snapshot are separate gates. Drift compares generated bytes to what is on disk, for generator-owned files only. The snapshot compares everything the generator emits to a baseline file. A change to a developer-owned template, such as App.tsx.ejs, passes drift and fails the snapshot, which is the intent: you review it as part of the change.

7. Reading a red check

SymptomLikely causeFirst move
Generate-and-diff or drift lists a file under platform/A hand edit to a generator-owned file, or a template change without regenerating.Regenerate and commit. Never keep a hand edit there.
Drift is red in CI, green on your machineStale build. The script resolves the codegen package to its compiled output.npm run clean && npm run build, then rerun.
Snapshot shows a diff you did not expectA template or generator change reached files you did not think about.Read the diff. It is never noise. Regenerate only if it is intended.
Consistency fails on a versionA pin changed in the generator but the example's package.json still has the old one.Update the example's dependencies, then rerun consistency and drift.
seans-mfe-tool: command not found in the build stepThe CLI is not on PATH in this CI image.Install it before the build. See section 2.
Validate fails with hosts-declaredThe manifest has no hosts: list.Add the shell's control-plane namespace, or scaffold with --host.
Publish shape fails with a missing templateA package does not list its templates in its published files.Fix the package's files list.
Swift or Rust fails on a type errorThe emitted code does not compile. Text-based tests cannot see this.Reproduce with check:swift-build or check:rust-build if you have the toolchain.
Composition fails waiting for a serviceAn image built but the service did not start, or the remote entry is missing.Read the container logs the job saved.

8. How this page reaches the site

The Publish docs site workflow owns the whole site. scripts/assemble-site.js copies each HTML page into _site/, and scripts/check-site.js fails the build on a broken link or an external asset. This page is self-contained, with no external fonts, scripts or images, because that check rejects them.

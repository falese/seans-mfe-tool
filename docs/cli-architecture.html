Generator CLI Schematics

Six drawings of how the CLI is put together: which packages exist and what depends on what, what happens when a command runs, how a manifest becomes files, where new frameworks and plugins attach, where the schemas come from, and how an agent reaches the same commands a person does.

Figure 1 — packages

Twelve packages in four tiers

Dependencies run one way, downward. contracts sits at the bottom and depends on nothing; the CLI sits at the top and depends on the plugins. runtime and control-plane are separate deployables — they ship to generated MFEs and to a running fleet, not into the CLI.

Figure 2 — dispatch

One invocation, exactly one line of stdout

Every command extends BaseCommand and implements runCommand(), never run(). That inversion puts one place in charge of turning a typed return value into the envelope, and keeps everything else — progress, warnings, diagnostics — on stderr.

Figure 3 — generation

A manifest becomes files, and each file gets an owner

mfe-manifest.yaml is the only input. Four phases, each reasonable about on its own: validate to a typed manifest, plan a render model, turn that into a list of file specs, then emit. Every spec carries an owner, and the owner decides what a second run does.

Figure 4 — extension

Two things plug in, and the core names neither

A framework variant and a capability plugin supply the same pair: a template root they own, and a list of file specs. resolveFilePlan reads that pair and contains no framework name and no plugin name.

Figure 5 — schemas

Nothing in a schema is written by hand

Two contracts are published as JSON Schema, and both are derived from the code that already enforces them. Command schemas come out of the live oclif registry and the TypeScript compiler; the manifest schema comes out of the Zod definition the parser runs.

Figure 6 — agent surface

Every tool call forks a process

The MCP server does not call command code in-process. It spawns the CLI with --json and parses one line back. The cost is a process per call; what it buys is that process.exit and working-directory changes cannot escape the child.

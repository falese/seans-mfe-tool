Business system map · seans-mfe-tool

A platform that lets many teams build one product together.

Teams build and release their own capabilities independently. The platform supplies the standards and controls that make those separately-built capabilities behave like one coherent product.

Nobody logs into this repository. It is the machinery underneath a product — and its whole purpose is to remove the trade-off between letting teams move fast and giving customers one consistent experience.

Read the first three sections and you have the whole story — about a minute. Nothing below needs to be clicked to be understood; the controls only add depth. Engineers: turn on Show technical implementation in the bar above to reveal repository paths throughout.

1 · Why it exists

The problem is not the teams. It is what happens between them.

One digital product, many teams changing it. Every team needs to move on its own schedule — and the moment they do, each one starts making the same decisions again, separately, in its own way. The platform does not take autonomy away. It removes the part of autonomy nobody wanted.

Without it — what the friction actually is

Six costs that grow with every team you add

  • Different approaches. Each team invents its own way to start up, fail, refresh and report health.
  • Repeated decisions. The same packaging, data-shaping and error questions get re-answered per team.
  • Integration friction. Connecting two capabilities is a bespoke negotiation, every time.
  • Release coordination. Shipping anything means agreeing a date with everyone else.
  • Inconsistent experience. The seams between teams become visible to the customer.
  • Growing complexity. The cost is not linear — it grows with the number of pairs of teams.

With it — what the standard supplies

The decisions a team no longer has to make

  • How to behave. Ten abilities every capability has, in a defined order, with defined failures.
  • How to be placed. One grammar for naming a space on a screen, shared by everyone.
  • How to be built. One command turns a written description into a running capability.
  • How to be released. Each capability ships as its own unit; nothing else rebuilds.
  • How data looks. One clean shape out, however messy the systems underneath are.
  • Where it appears. Decided by rules held outside the capability, changeable without a release.

The point is not that teams are the problem. Teams building independently is the goal. The platform exists so that independence costs the customer nothing — autonomy in what a team builds, agreement on how it plugs in.

The value proposition

Four promises

Everything on the rest of this page exists to keep one of these four promises.

Promise 01

Team autonomy

A team owns one capability end to end — what it does, what technology it is written in, and when it ships. Two front-end technologies are supported today by the same platform, and both reference products release capability by capability.

packages/framework-react/ · packages/framework-angular/ · examples/*/docker-compose.yaml

Promise 02

Shared standards

Every capability, whoever built it, offers the same ten abilities in the same order, names screen spaces with the same grammar, and fails in the same describable ways.

packages/contracts/ · packages/runtime/src/base-mfe.ts · slot-grammar.ts

Promise 03

Faster change

A team does not need to clear its implementation choices with every other team, and does not need a shared release train. Where a capability appears can be changed by editing rules rather than shipping code.

examples/*/control-plane/control-plane.yaml · packages/control-plane/

Promise 04

One customer experience

The customer sees a single product. The shell holds only empty labelled spaces; capabilities arrive and fill them, and if one fails the rest of the screen stays up.

examples/*/shell/ · packages/runtime/src/layout-manager.ts

2 · The core idea

One intent, five steps, one experience

If you remember one diagram from this page, make it this one. A team writes down what it wants. A factory turns that into working software. A house standard makes the result predictable to everything else. A control tower decides when and where it appears. The customer just sees a product.

The same idea, drawn across the two halves

Read it top to bottom. The top row happens once, when a team builds something. The bottom row happens every time a person clicks. The strip in the middle is the agreement that connects the two.

3 · Follow one feature

What actually happens to a single capability

Nine steps, from someone wanting something to a customer seeing it. Both examples below are real capabilities in this repository, built with the real toolchain. Pick one — the steps stay the same, only the specifics change. That is the whole claim of the platform, demonstrated.

Following: a berth tile (Meridian Station, Angular).

  1. 1

    Intent

    Someone needs something

    This is where a team decides what a capability should do for the business. No technology yet — just a need and an owner.

    For the berth tile

    Station operators need all six docking berths visible at a glance on one console, without opening six screens.

    examples/meridian-station/README.md · STATION-DEMO.md

    For Letter Pop

    The arcade needs another game — and the team that builds it should not have to touch the arcade, or any of the other twelve games.

    examples/abc-kids/README.md

  2. 2

    Definition

    The team writes it down, once

    One short file describes the capability: what it offers, what data it needs, what technology it is written in, and which spaces it is willing to fill. This file is the source of truth for feature intent — not for live data, not for what is deployed, not for what a customer currently sees.

    For the berth tile

    One brief declares three capabilities — a full docking board, a single berth tile, and a traffic log — plus the two backend systems it reads from. It says the team writes Angular.

    examples/meridian-station/meridian-docking-control/mfe-manifest.yaml

    For Letter Pop

    One brief declares three capabilities — play the game, show its cover card, and return its metadata. It says the team writes React.

    examples/abc-kids/letter-pop/mfe-manifest.yaml

  3. 3

    Build time

    The factory turns intent into software

    The platform reads the brief and writes out a complete, runnable capability: the application shell, the lifecycle wiring, its own data service, container packaging and tests. The team starts from something that already works and already complies.

    For the berth tile

    One command produces the Angular application, its lifecycle wrapper, and its own data service — including the translations that hide one backend's underscore naming and another's wrapper envelopes. The mess stops at the data service.

    packages/codegen/ (44 templates) · seans-mfe-tool remote:generate

    For Letter Pop

    The same command, a different technology adapter: a React application, the same lifecycle wrapper, the same packaging shape. The factory did not need changing to support both.

    packages/codegen/ · packages/framework-react/

  4. 4

    Build time

    The team writes the part only it can write

    The actual business logic — the thing that makes this capability worth having. The factory owns the platform plumbing and re-stamps it; it never overwrites what the team wrote.

    For the berth tile

    The docking team writes the tile component itself: what a berth looks like, what "occupied" means, when to show a warning. Nobody else has an opinion about it.

    .../meridian-docking-control/src/features/BerthTile/BerthTile.component.ts

    For Letter Pop

    The team writes the game. None of the game leaks into the platform, and none of the platform's opinions leak into the game.

    examples/abc-kids/letter-pop/src/features/

  5. 5

    The house standard

    It inherits the common standard

    The generated wrapper makes the capability predictable to the rest of the platform: it can be started, shown, refreshed, health-checked, described and queried — in a defined order, with defined failures — by a system that knows nothing about how it was built.

    For the berth tile

    An Angular capability that the runtime drives exactly the way it drives a React one. The platform never learns the word "Angular".

    packages/runtime/src/base-mfe.ts · .../src/platform/base-mfe/mfe.ts

    For Letter Pop

    The same base class, a different technology. This is the step that lets an arcade load a React game and a station console load an Angular tile through the identical mechanism.

    packages/runtime/src/base-mfe.ts · remote-mfe.ts

  6. 6

    Release

    It ships on its own

    The capability is packaged and released as its own unit, on its own schedule. Adding it or changing it does not rebuild anything else in the product.

    For the berth tile

    Its own container image, its own address. The docking team ships when the docking team is ready.

    .../meridian-docking-control/Dockerfile · examples/meridian-station/docker-compose.yaml

    For Letter Pop

    Its own container image, its own address. Adding a fourteenth game does not touch the other thirteen.

    examples/abc-kids/letter-pop/Dockerfile · examples/abc-kids/docker-compose.yaml

  7. 7

    Run time

    The control tower is told when to use it

    A rule — written outside every capability, in the product's own composition document — says which capability appears, in which named space, under which conditions. Change the rule, change the product; no team ships code.

    For the berth tile

    One rule covers all six berths: when the console asks for a berth, place a berth tile in the space named after that berth, and tell it which berth it is.

    examples/meridian-station/control-plane/control-plane.yaml → rules.json (generated)

    For Letter Pop

    One rule covers all thirteen games: when the arcade opens a game, place that game's play capability into the arcade's main space, and its cover into the information space.

    examples/abc-kids/control-plane/control-plane.yaml → rules.json (generated)

  8. 8

    Run time

    The screen assembles itself

    The screen is not built by anyone. A host publishes empty named spaces; the control tower resolves which capability belongs in each; a placer inserts them as they arrive, waits for spaces not yet open, and keeps the rest of the screen alive if one fails.

    For the berth tile

    The station console publishes three kinds of space — a main work area, a status rail, and one space per berth. Six tiles arrive from one capability and fill six of them independently.

    .../meridian-console/mfe-manifest.yaml (providesSlots) · packages/runtime/src/layout-manager.ts

    For Letter Pop

    The arcade home page publishes two spaces — main and information. The game goes to one, its cover art to the other.

    examples/abc-kids/home/mfe-manifest.yaml (providesSlots) · packages/runtime/src/layout-manager.ts

  9. 9

    The customer

    A person sees one product

    None of the above is visible. The customer sees a single, coherent product — and could not tell you how many teams, technologies or releases were involved.

    For the berth tile

    An operator sees one station console: a berth strip, a docking board, a traffic log, life support, cargo and crew — from six independently released capabilities.

    examples/meridian-station/shell/

    For Letter Pop

    A child sees one arcade with thirteen games. Thirteen independent releases, one experience.

    examples/abc-kids/shell/

4 · What the platform does

Ten capabilities, grouped by what they do — not where the files sit

This is the platform's job list. Four of these are foundational — shared by everything and depended on by everything else. The rest is the working machinery on top. None of these is a folder; several span packages, and several packages contribute to more than one.

Design intent · foundational

Feature definition

A single short document per capability, written by the team that owns it, declaring what it does, what data it needs, and which spaces on a screen it can fill.

Why it matters It is the source of truth for feature intent. The code, the data feed, the packaging and the validation are all derived from it, so the description and the shipped software cannot quietly disagree. It is deliberately not the source of truth for runtime state, live data or what is currently deployed.

packages/dsl/ · mfe-manifest.yaml (21 in the repository) · schemas/dsl/

Build machinery

Generation & build

Reads a definition and writes out a complete, runnable capability — user interface, wiring, data access, container packaging and tests.

Why it matters New teams start from a working, compliant capability instead of a blank page. It is also how a platform-wide improvement reaches everyone: change the factory, re-stamp the fleet, and a drift check proves nothing was missed.

packages/codegen/ · 44 templates · src/commands/remote/

Build machinery

Technology adapters

Small plug-ins that teach the factory a new front-end technology. Two ship today; adding a third is a new plug-in, not a change to the factory.

Why it matters This is what makes "any team, any technology" real rather than aspirational — and it means a technology choice made today does not become a platform-wide migration tomorrow. The framework field is deliberately an open string, not a fixed list.

packages/framework-react/ · packages/framework-angular/ · src/framework/loader.ts

Foundational

The house standard

Ten things every capability must be able to do — start up, show itself, refresh, check access, report health, describe itself, publish its data shape, answer a data question, raise an event, and report state upward — plus strict rules about the order they may happen in.

Why it matters This is the platform. It is the reason a capability built by one team in one technology can be operated by a system that knows nothing about either.

packages/contracts/ · packages/runtime/src/base-mfe.ts

Foundational

Placement contract

Every host publishes the spaces it offers by name — "main", "status", "berth 4" — and business rules target those names. Names are declared in the definition, never inferred from screen position.

Why it matters A layout redesign does not break the rules that decide what goes where. It also lets one capability appear six times on one screen, each instance independent and independently addressable.

docs/slot-contract.md · packages/contracts/src/slot-grammar.ts · slot-contract.ts

Working machinery

Runtime composition

Three cooperating roles: a rule book that turns "this person did this" into "show that capability", a router that carries the request and the answer, and a placer that puts the result into the right named space and keeps it healthy.

Why it matters Business rules about what appears where live outside the capabilities, so they can change without any team shipping code. It is also the single point every screen depends on.

packages/control-plane/ (registry + daemon) · packages/runtime/src/layout-manager.ts

Working machinery

Composition authoring

Each product has one composition document — a readable list of "when this happens, place that capability there". It is compiled into the payload the control tower actually reads; the payload is never hand-edited.

Why it matters Product placement becomes an editable business document rather than code spread across teams. A single rule can cover thirteen games or six berths, and a check fails the build if the compiled payload and the document disagree.

examples/*/control-plane/control-plane.yaml · packages/dsl/src/control-plane-compiler.ts

Working machinery

Data & integration

Each capability gets its own small data service that fronts the company's real systems and hands back one clean, consistent shape — no matter how inconsistent the sources are underneath.

Why it matters Legacy dialects stop leaking into feature teams' work. The reference product deliberately fronts systems that name the same thing different ways and wrap their answers differently, to prove the translation actually happens.

packages/bff-plugin/ · src/commands/api.ts · examples/meridian-station/*/specs/

Working machinery · partly complete

Access & identity

A place in the standard for every capability to check whether the current person may use it, a signature-verifying token handler in the runtime, and request identity carried into every data call.

Why it matters The seam for authorisation is designed and present at every boundary. The policy is not: the check that generated capabilities inherit approves everyone, and the data layer decodes the caller's token for identity without verifying it. Anyone planning a production rollout should read this as designed-but-unfinished.

packages/runtime/src/handlers/auth.ts · doAuthorizeAccess() · platform/bff/mesh-context.js

Foundational

Operator interface

One set of commands does everything above — start a capability, build it, check it, package it, deploy it, compile a composition. The identical commands are also published as tools that AI assistants can call directly.

Why it matters Humans and AI assistants drive the platform through exactly the same door, so anything an assistant does is reproducible by a person, and vice versa. Each assistant call runs in its own isolated process.

src/commands/ (19 published commands) · src/mcp/ · schemas/

Foundational

Governance & drift control

Automated checks that re-derive every reference capability from its definition and fail if the shipped code has drifted; that confirm each definition agrees with its packaging; that keep recorded decisions and published documentation consistent with the code; and that warn teams when a platform change reaches files the platform does not own.

Why it matters This is what keeps 21 independently-released capabilities honest without a release train. It is also the platform's answer to a real incident — see the trade-offs section.

scripts/check-mfe-drift · check-mfe-consistency · check-adr · packages/codegen/src/platform-migrations.ts

The payoff

What this architecture enables

Seven things this platform makes possible that are hard without it. Each is marked fact where the repository demonstrates it directly, or inference where it is a reasonable reading of the evidence.

  1. fact

    Teams can work independently while still adhering to shared standards.

    21 reference capabilities across two products, each with its own definition, its own container image and its own address. Every one of them inherits the same lifecycle from the same base class, and a drift check re-derives all 21 from their definitions on every change.

    examples/*/mfe-manifest.yaml · scripts/check-mfe-drift.ts

  2. fact

    Capabilities compose into one product experience without knowing about each other.

    A host publishes named spaces; capabilities declare which spaces they can fill; rules held outside both decide what goes where. A capability is never wired to another capability — only to a name. One capability fills six berth spaces on one screen, each instance independent.

    providesSlots in each manifest · packages/runtime/src/layout-manager.ts

  3. fact

    Platform decisions are made once, not re-invented per team.

    Lifecycle order, timeout behaviour, retry policy, error classification, slot naming and message shape all live in one dependency-free foundation package that every other part depends on. A team adopting the platform inherits all of it and decides none of it.

    packages/contracts/ · packages/runtime/

  4. fact

    Product placement can change without touching feature implementation.

    Each product's composition is a separate readable document compiled into the payload the control tower reads. Moving a capability, adding a berth or adding a game is an edit to that document — one rule already covers thirteen games and another covers six berths.

    examples/*/control-plane/control-plane.yaml · compose:build

  5. fact

    Different implementation technologies participate through one contract.

    React and Angular capabilities are driven identically by the runtime, and the technology field in a definition is deliberately an open string rather than a fixed list — an unknown value warns rather than fails. Supporting a third technology is a new plug-in package, not a change to the factory or the standard.

    packages/framework-{react,angular}/ · FrameworkSchema (open string)

  6. fact

    Humans and AI assistants operate the platform through the same door.

    All 19 published commands are exposed as assistant-callable tools generated from the same schemas, each call isolated in its own process. Two capabilities in the spaceport product were built through that interface rather than by a person typing, and the comparison was written up.

    src/mcp/ · schemas/ · examples/meridian-station/DX-REPORT.md

  7. inference

    A new team can be productive without reading the platform's source.

    The route in is: write a definition, run one command, fill in the business logic, add a rule. Everything else is inherited, and validation tells a team when it has broken a rule. This is an inference — the repository shows the mechanism and 21 worked examples, but contains no evidence about onboarding time for teams outside the project.

    docs/getting-started.md · mfe:validate

6 · The honest part

What this architecture trades off

Every one of the benefits above is bought with something. These five costs are visible in the repository itself — several of them documented by the team that built it, which is a maturity signal rather than a criticism. Anyone deciding whether to adopt this should price them in.

  1. trade-off fact

    A platform-wide change can reach code the platform does not own — silently.

    The factory owns some files and re-stamps them; it deliberately never touches others, because teams edit those. When one platform-wide change landed, 48 files needed updating: regeneration reached 29, and 19 were left stale with every automated check still passing. A human found them by grepping.

    A warning registry now exists specifically for this, and adding an entry is a required part of any platform change. But the underlying cost is structural: the platform can improve faster than it can safely propagate. This is the sharpest complexity point in the system.

    packages/codegen/src/platform-migrations.ts · docs/platform-design-review/breaking-change-regeneration-dx-report.md

  2. trade-off fact

    Governance is not optional — it is load-bearing machinery.

    Keeping 21 independently-released capabilities coherent without a release train requires a standing investment: drift checks, consistency checks, decision-record consistency checks, generated-documentation checks, composition validation, and a schema regeneration gate. Several of these must be run in a specific order, and at least one silently checks a stale build if the packages were not rebuilt first.

    An organisation adopting this inherits the checks as well as the platform. Without them, the independence the platform grants becomes the fragmentation it was built to prevent.

    CLAUDE.md "Verification gates before push" · scripts/check-*.ts

  3. trade-off fact

    Everything funnels through one foundation — high leverage, high blast radius.

    A single dependency-free package holds the shared standard, and every other part of the platform depends on it. That is excellent discipline, and it is also the reason a rename inside it can change generated code in 21 capabilities with no runtime file anywhere in the diff — the project's own memory file flags exactly this.

    The benefit and the risk are the same property. There is no version of this platform where the contract is both universal and cheap to change.

    packages/contracts/ · CLAUDE.md "Platform changes that reach generated code"

  4. trade-off fact

    Run-time composition means run-time coordination — and a shared point of dependence.

    Because placement is decided while a person is using the product, every screen depends on the control tower being reachable and correct. In the reference implementation the registry keeps its state in memory with a time-based eviction, so a restart forgets which capabilities exist. Debugging also crosses boundaries: a problem may live in a capability, in a rule, in the placer, or in the connection between them.

    Durability and production operation of the control tower are unfinished work, not solved problems.

    packages/control-plane/registry/simple-registry.js

  5. trade-off inference

    The standard has a designed hole where authorisation policy belongs.

    Checking access is one of the ten standard abilities, and a signature-verifying token handler exists in the runtime. But the check that generated capabilities inherit approves everyone, and the data layer decodes the caller's token to extract an identity without verifying its signature.

    The reading here is that the place for authorisation is properly designed and the policy is deliberately left to whoever adopts the platform. That is an inference from the code, not a statement the repository makes. Either way, a production rollout should treat authorisation as work not yet done.

    packages/runtime/src/handlers/auth.ts · doAuthorizeAccess() → true · platform/bff/mesh-context.js

Two more things worth knowing before deciding

  1. fact

    This is two systems that happen to live in one repository.

    A build-time factory and a run-time platform. They share a vocabulary but almost nothing else, and they can be adopted separately — you could use the factory without the control tower. Budgeting, staffing and roadmapping should probably treat them as two products.

  2. inference

    Maturity is uneven, and honestly reported.

    The build side is described as complete; the run-time platform is still in progress; the shared packages are not yet published for outside use; and packaging targets a local development container rather than a production environment. The project's own status page warns that it drifts and points to generated sources instead. Read this as a strong internal platform approaching, but not yet at, external readiness.

    docs/PROJECT-STATUS.md · docs/MERGE-PLAN.md

Why the demo products matter more than the counts

Both reference products are rebuilt from their definitions on every change and compared byte for byte against what is committed. The second product exists specifically to model messy reality — backend systems that name the same thing different ways and wrap their answers differently, with deliberate gaps in the data. inference That is a maturity signal: the platform is being tested against inconvenient truth, not a clean demo.

Where the repository was ambiguous

Places where the evidence ran out and a judgement was made, so you can check it.

There is no end customer here

"Customers & staff" appear on the map, but this repository contains no product they would use — only the machinery, plus two demo products. The customer is drawn because the run-time story is meaningless without one.

"Control tower" is a composite

Three separate things — a rule book, a router and a placer — are drawn as one idea in the executive views. They are genuinely separate components with separate failure modes; the detailed map splits them.

Production deployment is unclear

The packaging command targets a local development container, and the demo control plane keeps state in memory only. How any of this runs in a real production environment is not described anywhere in the repository, so nothing on this page claims to.

Two demo products, two different builders

The older product was assembled with a bespoke script; the newer one with the real toolchain, and it says so. Where the two disagree, the newer product was treated as the accurate picture of how the platform is meant to be used.

"Business capability" is the platform's word

The repository's own framing is that a capability equals one domain capability owned by one team. That is an aspiration expressed in documentation as much as an observable property of the code — the demo capabilities are games and spaceport screens, not, say, Payments or Claims.

The count of "capabilities" is a judgement

Ten groupings were chosen for comprehension. The repository has nine shared packages, but they do not map one-to-one: the house standard spans two packages, and the operator interface spans several directories.

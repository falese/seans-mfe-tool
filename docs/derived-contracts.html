Derived Contracts

Where every published contract in this platform comes from, what keeps it true, and the one class of error no amount of generation can reach.

The rule

Every published contract is derived from the code that already enforces it, and a gate fails when the committed artifact disagrees.

01Three audiences, one set of facts

seans-mfe-tool is three things at once, and each reads the same facts through a different lens.

It isIts contract is read by
a CLI a person typesa developer reading --help
a library another package importsa compiler resolving types
a tool surface an agent callsan MCP client validating JSON

All three need to know what a command accepts, what it returns, and what a manifest may contain. The cheap way to serve three audiences is to write the answer three times. That is also the way it ends up wrong in at least one of them — silently, because nothing compares the copies.

The measured cost of the cheap way

Every item below was found in this repository, not hypothesised.

  • build:* had no schema entry at all, so an agent could scaffold and validate an MFE over MCP but never build one.
  • deploy advertised eight flags the command did not have. Any agent using them got a hard parse failure.
  • remote:generate returned a preserved field absent from a schema declared additionalProperties: false — so a validating client rejected every successful response. Same for bff:validate's manifest and meshConfig.
  • Four documents described the manifest language. The one titled “the complete platform contract that ALL MFEs must conform to” was the most stale of them: it did not know the slot contract existed.
  • Two packages read the same manifest.transforms field against two different tables. [filterSchema] was rejected by the DSL validator and accepted by codegen; [filter-schema] was the reverse. Whichever spelling an author picked, half the platform objected.

Derivation is the answer, and the emphasis matters. Not “documented next to.” Not “kept in sync by a checklist.” Derived — so the artifact cannot say something the implementation does not, because nobody is writing the artifact.

The generalisation

This is the same rule applied to the ADR index and the API reference, stated once: generate the page the reader is least able to verify. A reader can check a code sample by running it. Nobody checks a JSON Schema without the source of truth in front of them — which is exactly the situation where a wrong one survives longest.

03Two lanes, one rule

The system has exactly two derivation lanes. They share the rule and share nothing else — different sources, different mechanisms, different artifacts.

04Deep dive — the command contract

Selection: which commands become a contract at all

Generation starts from Config.load(REPO_ROOT) — the same resolution the CLI itself performs at startup, first-party plugins included. That choice matters more than it looks: the catalogue cannot describe a command set the CLI does not have, because it is asking the dispatcher rather than parsing source or reading a list.

Four filters then apply:

FilterWhy
!hiddenoclif's own signal that a command is not public
!isAliasEntryoclif lists an alias as its own registry entry, distinguishable only by its id appearing in its own aliases array. Without this, adr:doctor and mfe:doctor each produce a duplicate tool for a command already catalogued
isFirstPartyseans-mfe-tool, @seans-mfe/*, @falese/*. Everything else is infrastructure that happens to be installed
!CATALOG_EXCLUDEDTwo entries, each with a written reason
The exclusion list is two lines, on purpose

Its comment says why: “deliberately not a place to park real gaps.” mcp:serve is excluded because advertising it offers an agent a tool that starts another copy of the server it is talking to. schemas is excluded because it lists the catalogue, which the agent already gets from tools/list. build:* is absent from the list on purpose — its absence from the catalogue was the original defect this module exists to close.

The input half

Args first, because declaration order is argv order; then flags. Three details worth knowing.

TRANSPORT_OWNED is subtractive, not decorative. json, interactive and cwd are stripped from every input schema. --json is appended to every child invocation by the MCP transport and the envelope contract depends on it, so letting a caller set it is a way to break the response rather than a capability. cwd is the reserved execution argument the registry injects on every tool — it must not also arrive as a command flag.

x-positional preserves what JSON Schema cannot express. A JSON object has no order; argv does. The extension records which properties are positional and in what order, so the transport can reassemble a real command line from a flat object.

The output half — this is the interesting part

A command's result type is a TypeScript artifact. It does not exist at runtime; there is nothing to introspect. So this lane does not run the command — it runs the compiler.

Step 1 — find the type. Walk the source file's top-level children for a default-exported class, then its extends heritage clause, then a type argument on BaseCommand:

export default class MfeValidate extends BaseCommand<MfeValidateResult> {
//                                  ───────────  ─────────────────
//                                    matched      the T that is extracted

checker.getTypeFromTypeNode(arg) turns that syntax node into a real ts.Type. A command with no type argument yields undefined — which is a hard failure, not an empty schema.

Step 2 — convert it. Deliberately narrow. The module states the reason: a type too complex to express is a signal about the result type, not a reason to widen this.

TypeScriptJSON SchemaNote
string, number, boolean, nullthe obvious—
unknown, any{}constrains nothing, says nothing
object{type:'object'}TS flags the bare keyword NonPrimitive, not Object — an easy miss
'a' | 'b'enum—
string | nulltype: ['null','string']sorted, because TS does not guarantee union member order and these files are under a byte-for-byte gate
a?: stringstring, omitted from requiredTS models this as string | undefined; optionality belongs in required, not in the member schema
a union of object shapes{}would need oneOf; no command result uses one, and guessing is worse than silence

Step 3 — lift the prose. Inside the object converter, for every property:

const description = ts
  .displayPartsToString(prop.getDocumentationComment(checker))
  .trim();
if (description) schema.description = description;

The JSDoc written to explain a field to a human reading the TypeScript becomes the description an agent reads when deciding whether to call the tool. One sentence, two audiences, no synchronisation step and no second place to forget. This is the single highest-leverage line in the system.

Step 4 — inherit. getPropertiesOfType flattens inheritance, so a field from MutatingResult lands in the schema beside the command's own. A command cannot publish a narrower envelope than it returns by forgetting what it extends.

Step 5 — close the object, carefully.

const indexInfo = checker.getIndexInfoOfType(type, ts.IndexKind.String);
if (!indexInfo) return false;  // safe to close

additionalProperties: false is what makes a future undeclared field fail loudly rather than silently break validating clients. But a type declaring [key: string]: unknown says extra keys are legal. Closing it anyway publishes a schema stricter than the type it claims to describe — precisely how bff:validate's manifest field came to be rejected by its own contract.

One compiler option, pinned on purpose

const program = ts.createProgram([...files.values()], {
  ...parsed.options,
  noEmit: true,
  skipLibCheck: true,
  strictNullChecks: true,
});

Redundant today, because the repo compiles strict — and kept deliberately, because it was not redundant when written. Under the previous strict: false, string | null collapsed to string, and the published schema claimed EnvCheckResult.found was always a string while build:check really returns null for a missing tool. Pinning it here means the contract's fidelity does not depend on an unrelated config file.

Two failure modes made loud

No derivable output type is a build failure, not an empty schema. The driver throws with a message naming the two legitimate resolutions — give the command a typed result, or exclude it with a reason. Emitting {} would have been the quiet option, and would have published a contract that promises nothing.

Filenames must round-trip. topic:command becomes topic-command.json, and every consumer recovers the id by turning each - back into a :. A hyphen anywhere in a command id is therefore ambiguous: control-plane:build would come back as control:plane:build, matching no command and failing three unrelated suites with no mention of the cause. Generation throws instead, where the fix is obvious.

05Deep dive — the manifest contract

Shorter, because Zod does the work. One schema feeds two consumers by two different mechanisms:

z.infer → the compiler. DSLManifest is inferred from the schema, never declared beside it. The generator receives a manifest that is already typed and already validated; there is no second definition to drift.

z.toJSONSchema → the artifact. One option is load-bearing: 

z.toJSONSchema(DSLManifestSchema, {
  target: 'draft-2020-12',
  unrepresentable: 'any',
})

The manifest language is deliberately open in places — framework and bundler are z.string().min(1) rather than enums, authorization is deferred. This renders those permissively instead of failing generation. Being unable to express an open field is not a reason to close it.

And then the docs. The field reference is generated from the generated JSON Schema, not from the Zod source. Field descriptions come from .describe() calls on the Zod fields themselves, so one sentence serves the schema, the editor tooltip and the reference page. It is the JSDoc trick from Lane A in a different notation.

06What an agent actually sees

The local MCP source walks schemas/ and turns each file into a tool: bff-init.json → mfe:bff:init, with schema.input as the inputSchema.

It filters on the presence of an input key. schemas/ holds two kinds of file: per-command contracts and standalone document schemas like manifest.schema.json. Only the former map to a runnable command, so only the former become tools — otherwise an agent is offered a tool whose call can only ever fail.

The registry then merges three sources — local, installed oclif plugins, and remote servers — and aborts startup on a name collision rather than letting one source silently shadow another.

A rule written as the reason for another rule

Every tool additionally accepts a reserved cwd, injected by the registry — which is why cwd appears in TRANSPORT_OWNED back in §04. The two ends of that rule are 200 lines apart in different packages. They agree because one is written as the justification for the other, not because someone remembered.

07The gates

Derivation without a gate is a convention. These make it a contract.

GateCatches
build → git diff schemas/Committed command contracts disagreeing with a fresh derivation
build:schema:dsl:checkA stale manifest schema. providesSlots shipped and was missing from the artifact for months, because this check existed but was never wired in
build:manifest-reference:checkA stale field reference
build:docs + git diff docs/apiA stale TypeDoc API reference
output-schema-conformanceWhat commands actually return, validated with ajv against what they publish
command-conformanceEvery catalogued command either exercised or excluded with a named reason

The conformance test looks redundant and is not. Output schemas are derived from the declared type, and TypeScript already enforces that a command returns it — so what is left? Its own header answers: “a belt over the compiler's braces.” It catches the gap the type system cannot see — a runtime as cast, a hand-built object literal that escapes the declared type, a field added by a helper. Cheap insurance on a link that is otherwise sound.

08What this guarantees — and what it does not

Guaranteed. The chain cannot break anywhere along its length, with no runtime validation involved.

Not guaranteed: that any of it is true.

Derivation guarantees agreement between places. It does not guarantee agreement with reality. This repository has a live demonstration:

Found in this codebase

A decision record redefined --force from does nothing to replaces developer-owned files. One command's flag description stayed 'Overwrite existing files'.

The pipeline faithfully republished that sentence into the published JSON Schema on every build, for months, where an agent read it as the tool's documentation. Everything was perfectly consistent the entire time it was wrong.

What caught it was a person reading the string against the decision record that superseded it. No gate here can do that, because every gate compares an artifact to a source — and the source itself was the thing that was wrong.

So, the honest statement of what this buys:

  • It removes transcription error entirely.
  • It does nothing about authoring error.
  • Its main cost is that the second is now the only kind left — which makes it both easier to find and easier to overlook.
A second instance, found while writing this page

The header of schema-derivation.ts still claimed “Output schemas stay hand-authored: a command's TypeScript result type is not introspectable at runtime.” That stopped being true when the output derivation landed. A module comment is prose about the system, so nothing derives it and nothing gates it — drift in the very module that exists to prevent drift.

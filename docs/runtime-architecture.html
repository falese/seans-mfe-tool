Runtime Platform Schematics

Eight drawings of what runs after the CLI exits: the class ladder generated code sits on, the state machine every MFE obeys, what one capability call does, how a slot gets filled, why an MFE written in any framework can fill it, and the two services that drive the loop.

Companion to Generator CLI Schematics, which ends where this begins. Prose references: docs/architecture-runtime-platform.md, docs/runtime-class-hierarchy.md, docs/slot-architecture.md and docs/architecture-composition-primer.md, none of which are published to this site — read them in the repository.

Figure 1 — the loop

Four parts in one loop

The registry holds what should be composed. The daemon pushes it. The shell's LayoutManager converges on it. The MFE renders and pushes state back, which can change what the registry holds. The remaining figures each detail one of these four.

Figure 2 — the class ladder

Four classes, with generated code at the top

Each rung adds exactly one thing and forbids what the rung above owns. BaseMFE is neutral and never mounts; BaseRemoteMFE adds module federation and is still neutral; only the concrete classes may import a UI framework, because they produce the framework-native handle.

Figure 3 — the state machine

Six states, with the legal transitions in a fixed table

MFE_LIFECYCLE_TRANSITIONS in packages/contracts/src/platform-contract.ts is the machine. A transition that is not an edge here is a programming error and throws at the boundary rather than corrupting state silently (ADR-042).

Figure 4 — one capability call

All ten capabilities run through one pipeline

load(), render(), query() and the seven others are the same machinery with different arguments. Each builds a middleware chain and hands it to runPipeline. The developer writes only the doCapability() in the middle.

Figure 5 — handler resolution

A hook name in YAML becomes a function, once, at module load

A manifest names hooks as strings. platform.* resolves against a Map built once from the handlers barrel; custom.* resolves against methods the MFE author wrote. The full set of resolvable platform names is visible at startup rather than discovered per call.

Figure 6 — slot convergence

How the layout manager moves actual state toward desired state

LayoutManager does not execute placement commands. It holds what the registry wants, desired: Map<address, experience>, and reconciles the DOM toward it. Placing an experience at a new address unplaces it from the old one, because a reverse index keeps the map bounded by live placements (ADR-066).

Figure 7 — the polyglot interface

Why a slot can hold an MFE written in a framework the shell has never heard of

Polyglot composition rests on four links: a framework-free slot address, a rule that binds by data, a mandatory imperative mount, and an optional tagged native handle. The slot contract supplies the first two, the presentation contract the last two. None of them carries a framework name.

Figure 8 — the two services

The control plane is 1,375 lines of plain JavaScript

Neither service imports anything from packages/. They are GraphQL servers in Docker images that a fleet deploys, not libraries anything links against. The CLI can be replaced without touching a running fleet.
